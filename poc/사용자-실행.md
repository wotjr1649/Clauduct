# 기존 Codex OAuth를 사용하는 사용자 실행 진입점

**현재 목표의 명령은 [실제 Read 1회](./실제-Read-실행.md)다:** `node D:\AIDEV\Clauduct\poc\claude-read-once.mjs --live-read-once`. SEND 후 astra-low·최대 2회 요청으로 실행한다. 로컬 검증은 완료했으며 실제 사용자 SUCCESS는 아직 받지 않았다. 아래 합성 OAuth/관찰 명령은 이전 기록이고 재실행을 요구하지 않는다.

**현재 다음 실행은 합성 OAuth 재검사가 아니라 [실제 Claude 요청 관찰](./요청-검사기.md)이다:** `node D:\AIDEV\Clauduct\poc\claude-inspection.mjs --inspect`. 공개 marker·최대 60초 검사 + 2초 정리·정제 JSON만 출력하며 Codex에 전송하지 않는다. 실행 파일의 로컬 검증은 완료했지만 실제 Read 1회 전체 PoC는 아직 미완료다. 아래 합성 OAuth 명령은 이전 증거로 보존한다.

2026-09-07 현재. **사용자 v5 결과 두 개를 수신했고 Astra low·Luna low 모두 SUCCESS로 확인했다.** 요청/연결 각 2회·정확한 최종 marker·call ID·자원 정리 true이며 실제 도구 실행은 0회다. 이 합성 도구 프로토콜 검사는 완료했으므로 같은 명령을 반복할 필요가 없다. 아래 명령은 실행 이력과 향후 필요한 회귀의 참고용으로 보존한다. 에이전트는 실제 인증을 읽거나 SEND를 입력하지 않았다.

1. Astra low를 한 번 실행하고 표시되는 확인에 SEND를 입력한다.

```powershell
Set-Location 'D:\AIDEV\Clauduct'
node .\poc\user-session.mjs --live-tool-roundtrip --profile=astra-low --allow-missing-content-type
```

2. 첫 프로세스 종료 후 Luna low를 한 번 실행하고 별도로 SEND를 입력한다.

```powershell
node .\poc\user-session.mjs --live-tool-roundtrip --profile=luna-low --allow-missing-content-type
```

각 SEND는 해당 모델의 **upstream 최대 2회**만 승인한다. 두 실행 전체로 최대 4회이며 각 실행은 도구 요청→합성 도구 결과→최종 답변을 검사한다. 한 SEND로 두 모델을 자동 실행하지 않는다. 첫 결과가 실패해도 사용자가 요청한 두 번째 모델의 비교는 별도 SEND로 선택할 수 있고, 실패한 모델을 자동 재시도하거나 대체하지 않는다. 두 결과의 requestedModel/requestedEffort를 확인하고 마지막 정제 JSON을 모델별 하나씩 공유한다. 토큰·계정 파일·헤더·응답 원문은 공유하지 않는다. 출력 리다이렉트나 파이프는 대화형 확인 조건에서 거부된다.

--profile 생략 시 astra-low다. astra-xhigh·임의 모델·effort·중복/복수 profile 인수는 사용자 진입점에서 거부한다. 이전 xhigh 결과는 과거 증거로 보존하고 새 low 결과와 같은 조건의 재실행으로 취급하지 않는다.

이 검사는 게이트웨이를 통한 실제 Codex 도구 프로토콜을 확인하기 위한 새 단계다. 이전의 정확한 OK·헤더 비교를 반복하지 않는다. Claude Code를 실행하지 않으며 도구 결과는 합성 문자열로 제공한다. 성공해도 실제 Claude Read·권한·hooks 왕복 성공으로 기록하지 않는다.

## 1. 한 번의 실행 흐름

1. 인수·입출력 TTY·runtime·고정 CODEX_HOME을 확인한다. 60초 안에 정확한 SEND를 받지 못하면 종료한다.
2. 기존 고정 codex.exe의 --version 결과가 0.153.4인지 확인한다. CLI 확인은 최대 5초이고 출력·오류 원문은 내보내지 않는다.
3. 기존 설정의 파일 캐시 모드를 확인하고 기존 OAuth를 메모리로 읽는다. access token·account·만료를 검사하며 keyring/auto, 잘못된 캐시, 만료는 요청 전에 중단한다.
4. 기존 OAuth를 Codex 전송 객체에 전달한다. 게이트웨이의 별도 난수 세션 비밀은 같은 프로세스의 검사 클라이언트만 메모리로 받는다.
5. 첫 Messages 요청으로 합성 Read 호출을 요청한다. 완성된 call ID·이름·정확한 고정 경로를 검사한다. 도구 호출이 없으면 추가 요청 없이 NO_TOOL_CALL로 종료한다.
6. 합성 tool_result를 같은 ID의 function_call_output으로 전송한다. 두 번째 요청은 tool_choice=none이며 최종 marker·정상 완료를 검사한다.
7. 게이트웨이·HTTP 클라이언트·upstream 소켓·타이머를 정리한 뒤 허용된 고정 분류·boolean·숫자만 출력한다.

실제 파일을 읽지 않는다. 모델이 보낸 경로는 고정 합성 경로와 비교하는 데이터이며 실행 명령이 아니다. 로컬 세션 비밀이나 OAuth를 명령 인수·환경변수·로그·임시 파일로 전달하지 않는다. refresh·인증 쓰기·계정 변경·재시도·모델 대체는 없다. 문자열 참조 해제는 managed 메모리의 즉시 완전 소거를 보증하지 않는다.

## 2. Codex 요청 조건과 한도

| 항목 | 현재 계약 |
|---|---|
| 목적지·모델 | https://chatgpt.com/backend-api/codex/responses, astra-low=gpt-6-astra/low 또는 luna-low=gpt-5.6-luna/low. 선택은 요청·전송 사전 검사·응답 검증·결과 JSON에 동일하게 적용 |
| 인증 | 기존 사용자 파일 캐시의 메모리 사용. 다른 저장소로 변경하거나 fallback하지 않음 |
| 버전 | 기존 검토값 0.153.4만 허용. 실제 사용자 실행에서 확인하며 에이전트가 이번에 CLI를 실행한 것은 아님 |
| 요청·응답 | upstream 최대 2회, 요청별 45초, 응답 256 KiB, 입력 64 KiB |
| 출력 토큰 수 | 사용자 검사 요청은 max_tokens/max_output_tokens를 처음부터 포함하지 않음. 토큰 개수에 의한 생성 상한은 없음 |
| instructions | developer 입력을 따르도록 하는 고정 안내 문자열. 원래 system의 블록·순서는 developer 입력에 보존 |
| 헤더 정책 | 기본 strict. 위 명령의 명시적 옵션은 기존에 승인한 필드 부재 호환 정책만 선택 |
| 종료 | 실패·취소 시 추가 요청 없음. 취소가 서버 추론·과금을 즉시 중단한다고 보증하지 않음 |

OmniRoute의 [Codex 요청 변환](../../_ref/OmniRoute/open-sse/executors/codex.ts)은 max_tokens와 max_output_tokens를 제거한다. 코드는 backend 거부를 이유로 설명하지만 이것은 참조 소스의 동작·설명이며 우리 계정에서 관찰한 응답은 아니다. 새 검사 클라이언트는 해당 필드를 만들지 않는다. 외부 클라이언트가 명시한 토큰 한도는 **TOKEN_LIMIT_UNSUPPORTED로 upstream 전송 전에 거부**한다. 조용히 삭제하지 않는다.

기존 오프라인 변환기의 숫자 대응 후보는 회귀 검사를 위해 보존했다. 그것이 Codex backend 지원을 입증하지 않는다. 실제 Claude 요청의 max_tokens 의미를 어떻게 수용할지는 별도 미해결 조건이다. 시간·바이트 제한을 토큰·비용 상한과 같은 것으로 설명하지 않는다.

기존 사용자 Node https/fetch/.NET 비교의 MISSING_CONTENT_TYPE / passed=false는 유지된다. 이 실행의 passed는 **별도 명시적 정책 아래 새 도구 프로토콜 왕복의 판정**이다. 빈 Content-Type·다른 media type·오류/불완전 본문은 계속 실패한다.

| CLI_VERSION_CHANGED | 검토 버전과 다르거나 버전 확인 실패. 제한 완화·자동 업데이트 없음 |
| FILE_CACHE_UNAVAILABLE / CREDENTIAL_STORE_UNSUPPORTED / INVALID_AUTH_CACHE / TOKEN_EXPIRED | 기존 캐시 조건을 충족하지 못함. keyring 전환·새 로그인·refresh를 자동 수행하지 않음 |
| UNAUTHENTICATED / FORBIDDEN / RATE_LIMITED / HTTP_ERROR | 해당 실패를 기록하고 종료. 인증·모델 변경이나 자동 재요청 없음 |
| NO_TOOL_CALL / INCOMPLETE_RESPONSE | 필요한 도구 호출 또는 정상 완료가 확인되지 않음. 성공으로 처리하지 않음 |
| SEQUENCE_MISMATCH / UNSUPPORTED_FIELDS / UNSUPPORTED_OUTPUT / UNSUPPORTED_EVENT / UNSUPPORTED_CACHED_USAGE 등 | Clauduct의 현재 파서 계약에서 거부. responseDiagnostics의 단계·이벤트·항목 분류로 다음 지원 범위를 판단 |
| REFUSAL / UPSTREAM_FAILURE | 파서에서 refusal 또는 upstream 실패/미완료 이벤트를 발견한 경우. provider 오류 원문은 출력하지 않음 |
| PROTOCOL_REJECTED | 허용된 오류 코드로 분류되지 않은 예외의 로컬 대체 이름. 서버가 보낸 거절 문구나 인증 거부의 증거가 아님 |
| UNSUPPORTED_MESSAGE_PHASE | commentary 또는 미지 phase 타입/값. 중간 메시지를 최종 완료로 처리하지 않음 |
| MODEL_EFFORT_MISMATCH | 완료 응답의 model/effort가 해당 실행의 고정 선택과 다름. 자동 교체나 재요청 없음 |
| FINAL_MARKER_MISMATCH | 두 번째 응답이 정확한 합성 결과와 다름. 성공으로 처리하지 않음 |
| TIMEOUT / DELIVERY_TIMEOUT / DISCONNECTED / CLEANUP_FAILED | 시간·연결·정리 실패. 추가 호출하지 않음 |

JSON의 upstreamMode는 live/synthetic/not-started로 경로를 구별한다. toolResultMode=synthetic과 toolExecutions=0은 실제 도구 실행이 없는 검사임을 표시한다. credentialWrites=0·retries=0은 이 프로그램의 코드 경로이며 OS 전체 감사를 뜻하지 않는다. 실패하면 그 JSON을 분석하기 전 동일 명령을 반복하지 않는다.

### 현재 — message 추가 필드의 정제 진단

최신 사용자 v4 결과는 마지막 HTTP 200·13,185바이트·Content-Type 부재·HTTP 프레이밍 완료, 18개 이벤트 중 다섯 번째 message item-added/in_progress, sequenceNumber=4/outputIndex=1이다. messagePhase=final_answer/messageExtraFields=phase-only로 추가 키가 phase뿐임을 확인했다. reasoningItemCount=1/reasoningEncryptedUpdates=1, 요청/연결 각 2회·도구 복원 1회·본문 호환 통과 1회·자원 정리 true다. 당시 전체 passed=false, UNSUPPORTED_FIELDS이며 최종 marker/usage는 아직 검증되지 않았다. 이 보고는 astra/xhigh이며 새 두 low 실행의 결과가 아니다.

v5는 시작/item.done/최종 output에서 선택적 final_answer/null/부재를 처리하며, commentary와 미지 값은 UNSUPPORTED_MESSAGE_PHASE로 거부한다. phase가 있다는 이유만으로 완료를 인정하지 않는다. 기존 v4의 두 분류는 유지한다. 이후 delta나 completed 이벤트에서는 마지막 메시지 필드 관찰을 유지하고 다음 요청에서는 초기화한다. 최종 response.output의 메시지도 관찰하므로 eventKind=completed일 때 메시지 분류가 있을 수 있다. 파싱만 했거나 앞 단계에서 실패해 메시지 필드 검사에 도달하지 못하면 not-observed다.

| 추가 진단 | 고정 값과 의미 |
|---|---|
| messagePhase | not-observed: 메시지 필드 검사 전. not-provided: phase 키 없음. null: 명시적 null. commentary/final_answer: 알려진 값. other: 나머지 타입/값. 임의 원문은 출력하지 않음 |
| messageExtraFields | none: 기존 id/type/status/role/content 밖의 키 없음. phase-only: 추가 키가 phase 하나뿐. other-only: phase 없이 다른 추가 키 존재. phase-and-other: 둘 다 존재. not-observed: 메시지 필드 검사 전 |

두 값은 **관찰 분류이며 성공 판정이 아니다**. messageExtraFields는 v4와 동일하게 기존 다섯 기본 필드 밖의 키를 분류하므로, v5의 성공 응답에도 phase-only가 표시될 수 있다. phase-and-other/other-only는 계속 실패한다. [phase 계약](../verification/최소-어댑터-PoC-명세.md#message-phase-지원-전-조건)의 모든 완료 조건을 함께 확인한다. 원문·임의 필드명·암호화 값·해시는 출력하지 않는다. 각 모델의 결과를 분석하기 전 같은 모델을 재실행하지 않는다.

### 이전 단계 — 시작·완료 암호화 비교의 원인 확인과 완료 snapshot 선택

사용자가 diagnosticVersion=3, SNAPSHOT_MISMATCH, snapshotCheck=REASONING_INITIAL_ENCRYPTED를 보고했다. 마지막 응답은 HTTP 200·Content-Type 부재·13,081바이트·httpComplete=true, 파싱한 18개 이벤트 중 네 번째 reasoning item-done/상태 부재/sequenceNumber=3/outputIndex=0이다. 요청/연결 각 2회, 첫 도구 복원 1회·본문 호환 통과 1회·완료 reasoning 수 0, 자원 정리 true이며 실제 도구 실행·인증 쓰기·재시도 0회다. 이는 사용자 증거이며 전체 왕복 성공은 아니다.

이 비교에 도달하려면 해당 이벤트의 응답 ID, reasoning ID/종류/명시된 상태, 출력 위치와 관찰된 텍스트 검사를 통과해야 한다. 시작의 비어 있지 않은 암호화 문자열과 item.done의 문자열이 다르다는 이유로 Clauduct가 실패했다. 차이가 발생한 서버 내부 이유·평문 내용·암호화 방식은 이 JSON으로 알 수 없으며 조사하거나 복호화하지 않는다.

공식 문서는 완료된 output의 reasoning을 후속 input에 보존하도록 설명한다. 암호화 문자열을 불변 ID로 간주할 근거는 확인되지 않았다. 수정 후에는 **item.added를 임시 상태, item.done을 완료 snapshot, response.completed.output을 최종 snapshot으로 구별**한다. 후속 input에는 완료 snapshot의 암호화 값을 그대로 전달한다. 최종 필드가 있으면 그 값(null/빈 문자열 포함)을 선택하고, 생략된 경우만 item.done 값을 보존한다. 시작에만 있는 암호화 값을 완료 데이터에 보충하지 않는다. ID·순서·상태·텍스트 일치·전체 완료·모델/effort/usage·크기 제한은 계속 검증한다. [본문 계약과 근거](./README.md#4-스트리밍상태한도)를 따른다.

diagnosticVersion=3은 유지하며 **responseDiagnostics.reasoningEncryptedUpdates**를 추가했다. 마지막 응답에서 시작→item.done 또는 item.done→최종 snapshot 양쪽에 문자열이 있고 값이 달랐던 횟수다. 명시적 null/필드 부재는 문자열 변경 수에 포함하지 않는다. 최대 이벤트 예산 안의 숫자만 출력하고 요청마다 초기화한다. 뒤의 검사에서 실패해도 관찰된 수는 남을 수 있으므로 양수만으로 전체 성공·복호화·후속 재사용 성공을 판단하지 않는다. 과거 REASONING_INITIAL_ENCRYPTED/REASONING_FINAL_ENCRYPTED 이름은 진단 호환 목록에 남지만 새 코드에서는 해당 암호화 동일성 오류를 발생시키지 않는다.

수정 후 1회 결과를 분석하기 전 명령을 반복하지 않는다. 실패하면 실제 분류에 따라 판단하며 자동 refresh·재요청·모델 교체나 원문 공유를 하지 않는다. 아래는 이전 진단 구현 기록이다.

### 이전 단계 — 두 번째 요청의 reasoning 실패 분석과 진단 보완

**후속 사용자 결과:** reasoning 추가 구현 뒤에도 전체 왕복은 실패했다. 요청/연결 각 2회, 도구 복원 1회·본문 호환 통과 1회, 마지막 HTTP 200·13,357바이트·httpComplete=true·Content-Type 부재. 파싱한 18개 이벤트 중 네 번째 item-done, reasoning/status 부재/sequenceNumber=3/outputIndex=0에서 SNAPSHOT_MISMATCH다. reasoningItemCount=0, 자원 정리 true, 실제 도구 실행·인증 쓰기·재시도 0회다.

코드상 이 위치에서는 제공된 response_id의 충돌, 완료 reasoning ID의 형식 오류, 시작·완료 item ID의 차이, 시작·완료 encrypted_content의 차이를 구별해야 한다. 이 중 어느 것이 실제 원인인지 기존 결과에는 없다. 특히 시작·완료 암호화 값의 동일성은 검증이 필요한 기존 파서 가정이며 이번 보고만으로 유지/제거의 근거가 확정되지 않는다. 원문을 저장·요청하거나 임의로 비교를 건너뛰지 않는다.

**현재 출력은 diagnosticVersion=3**이며 responseDiagnostics.snapshotCheck에 처음 실패한 snapshot 비교의 고정 이름을 추가한다. 오류 category와 모든 수용 조건은 유지한다. 값을 출력하거나 복호화하지 않고, 알려지지 않은 진단 값은 not-observed로 정제한다.

원인 진단 실행은 최대 2회 요청 후 종료하고 마지막 정제 JSON만 공유한다. 새 결과를 분석하기 전 반복하지 않는다. 새 비교 이름이 와도 먼저 계약 근거를 확인하며 ID 충돌이나 암호화 차이를 자동 수용하지 않는다. 아래 UNSUPPORTED_OUTPUT 기록은 이전 실행의 증거로 보존한다.

사용자 보고는 요청/연결 2회, reconstructedToolCalls=1, compatibilityApplied=1, resourcesClosed=true이며 전체 UNSUPPORTED_OUTPUT이다. 마지막 upstream은 HTTP 200·Content-Type 부재·13,037바이트·HTTP 프레이밍 완료, 헤더 검사/호환 통과다. 18개 이벤트 중 세 번째 item-added의 reasoning, status 부재, output_index=0에서 중단했다. 이 기록은 사용자 실행 증거다.

첫 도구 응답의 인수·고정 경로·usage 검증과 빈 완료 output 복원이 통과했고, 합성 tool_result를 포함한 두 번째 요청까지 진행한 코드 경로와 일치한다. callIdMatches/exactMarker=false는 전체 왕복 성공 assertion이 없다는 뜻이며 첫 단계가 다시 실패했다는 뜻은 아니다. 실제 도구 실행은 0회다.

파서는 status=in_progress인 단일 output_index=0만 가정했다. 이제 status가 없는 reasoning도 명시적 item.done과 정상 response.completed로 완료를 판정하고, 순차 reasoning 뒤의 한 메시지/도구를 실제 index로 검사한다. 명시된 실패/미완료 status는 계속 거부한다. reasoning의 summary/text delta·done·snapshot과 암호화 필드의 일관성을 검사하며 내용은 진단 JSON이나 하류 답변에 출력하지 않는다. 도구 호출 전에 받은 reasoning은 후속 Codex input에 원래 순서로 보존한다. [상세 본문 계약](./README.md#4-스트리밍상태한도)을 참고한다.

추가된 responseDiagnostics.reasoningItemCount는 마지막 응답에서 item.done 검증까지 통과한 reasoning 수다. 전체 완료·정확한 최종 답변의 증거가 아니며 category/passed와 함께 읽는다. reasoning만 있는 응답, snapshot·ID·순서 충돌, cache usage 미지원 등은 계속 실패한다. 요청 수·effort·인증·헤더 정책은 바꾸지 않았다.

이번 구현의 사용자 확인은 위 명령 한 실행이며 upstream 최대 2회다. 실패하면 JSON을 분석하기 전 반복하지 않는다. 과거 헤더 비교나 로그인 변경은 하지 않는다. 아래는 이전 단계의 증거다.

### 이전 단계 — 도구 snapshot 실패 분석과 수정

사용자 상세 결과는 HTTP 200, Content-Type 부재, 본문 11,682바이트, HTTP 프레이밍 완료, 헤더 검사/필드 부재 정책 통과, 26개 이벤트 중 마지막 completed에서 MISSING_TOOL_SNAPSHOT이다. 요청/연결 각 1회, 자원 정리 true, 실제 도구 실행/재시도/인증 쓰기 0회다. **이 요청의 실패는 인증 거부가 아니라 Clauduct의 완료 output 요구 조건이었다.** 에이전트의 라이브 실행 증거는 아니다.

해당 오류에 도달한 코드 경로를 대조하면 function_call의 delta·arguments.done·output_item.done 및 정상 response 완료·모델/effort 일치는 이미 검사됐고, 마지막 response.output=[]에서 중단했다. 앞선 완료된 도구 항목이 있는데도 마지막 응답에 같은 항목을 다시 요구한 것이다. 다만 오류 뒤에 있는 인수 JSON/고정 경로/usage 검사는 당시 수행되지 않았으므로 이 결과만으로 해당 조건까지 통과했다고 단정하지 않는다.

이제 마지막 output이 **정확히 빈 배열일 때만** 검증된 output_item.done을 재사용한다. delta와 arguments.done과 item snapshot의 인수 문자열, item ID/call ID/이름/상태/위치, 정상 response 완료, 고정 경로·usage를 모두 확인한 뒤에만 tool_use를 반환한다. 제공된 response_id와 arguments.done.name의 충돌 검사도 보강했다. 마지막 output이 존재하면 반드시 그것을 검증하고 충돌을 스트림으로 덮어쓰지 않는다. 완료 snapshot 또는 response 완료가 없으면 복원하지 않는다.

최상위 **reconstructedToolCalls**는 이 복원 경로로 본문 검증까지 통과한 도구 호출 수(0 또는 1)다. 실제 도구 실행 수나 전체 왕복 성공을 뜻하지 않는다. 두 번째 응답이 실패하면 이 값이 1이어도 passed=false다. 진단 버전은 호환되는 필드 추가이므로 2를 유지한다.

이후 사용자 결과에서 도구 복원은 통과했고, 두 번째 응답의 reasoning 항목에서 중단했다. 아래 포괄 오류 기록도 이전 요청에 대한 것으로 보존한다.

### 이전 단계 — 포괄 오류 진단 수정

사용자는 이전 버전에서 passed=false, PROTOCOL_REJECTED, upstreamMode=live, 요청/연결 각 1회, resourcesClosed=true를 보고했다. compatibilityApplied=0과 callIdMatches/exactMarker=false도 포함됐다. **그 결과에는 HTTP 상태와 내부 오류가 없어 실제 실패 원인을 복원할 수 없다.** 에이전트가 실행한 결과가 아니다.

당시 게이트웨이와 진입점의 오류 허용 목록에 여러 파서 오류가 빠져 있었다. 공유 목록으로 통일해 실제 고정 오류 코드가 최종 JSON까지 전달되도록 수정했다. 그 단계에서는 reasoning도 미지원이었으며 이후 상세 사용자 결과를 근거로 위 본문 계약을 구현했다. 이전 요청의 원인을 새 결과로 소급 확정하지 않는다.

수정된 출력은 **diagnosticVersion=2**이며 responseDiagnostics를 추가한다.

위 상세 사용자 결과로 다음 요청의 실패 지점은 확인했다. 이전 PROTOCOL_REJECTED 요청의 원문과 원인을 소급 복원한 것은 아니며 두 요청의 응답이 같았다고 주장하지 않는다.
