**현재:** 요청 관찰 v1/v2는 완료됐고 [실제 Read 실행 진입점](./실제-Read-실행.md)을 준비했다. 새 통합 22/22 및 기존 회귀를 통과했다. 이제 사용자 터미널의 `claude-read-once.mjs --live-read-once` 결과가 필요하며, 아래 관찰 재실행 안내는 이전 기록이다.

**최신:** 사용자 v2 결과를 수신해 role=user→system, effort=xhigh, Read 숫자 제약과 keep=all을 확인했다. **아래 v2 재실행 안내는 완료된 이전 단계이며 지금 다시 실행할 필요 없다.** [오프라인 입력 변환](../verification/최소-어댑터-PoC-명세.md)을 구현하고 어댑터 296/296·게이트웨이 74/74·사용자 합성 세션 89/89·검사기 90/90을 통과했다. 실제 live Read PoC는 미완료이며 토큰 한도·미분류 beta 등의 경계는 유지한다.

## 최신 — 사용자 v1 요청 관찰 성공, v2 의미 구분 보완

사용자가 제공한 diagnosticVersion=1 결과에서 실제 Claude 자식 시작·종료, messages 요청 **1회/29,906 bytes**, 공개 Bearer marker, model alias/API version 일치, 자원 정리 true를 확인했다. count_tokens/hello/거부/절단/timeout은 모두 0이고 beta·session ID가 있었다. 클라이언트 exitCode=1과 출력 폐기 650 bytes는 관찰값이며, 검사기의 의도적인 HTTP 400과 일치하는 결과다. 에이전트가 실제 Claude를 실행한 증거는 아니다. `actualReadVerified=false`를 유지한다.

| 실제 v1 관찰 | 현재 구현과의 차이 |
|---|---|
| max_tokens=64000 | 기존 오프라인 허용 범위 밖이며 live transport는 명시적 한도를 거부. backend가 직접 거부했다는 관찰은 아님 |
| messages 2개, user 1/other 1, text block 3개 | 기존 진단은 user/assistant 외 역할을 합쳐 정확한 역할과 순서를 잃었음. system/developer라고 추정해 승격하거나 user로 낮추지 않음 |

| Read 1개, offset/limit integer, pages string, additionalProperties=false | 실제 schema가 합성 fixture와 다름. offset/limit의 추가 키 각각 2개, root 추가 키 1개의 의미는 v1에서 미구분 |
| 다른 도구/EndConversation 0 | 해당 사용자 실행에서만 확인. 모든 Claude 실행의 도구 집합에 대한 보증은 아님 |

**v2 변경:** 첫 8개 메시지의 역할을 user/assistant/system/developer/tool/function/absent/other 고정값으로 순서대로 분류한다. thinking·metadata·output_config·context_management의 알려진 필드 존재/타입, 고정 effort, context edit 전략·threshold를 정제한다. Read의 minimum/maximum/exclusiveMinimum/exclusiveMaximum/default는 타입과 음이 아닌 safe integer만 출력하며 그 외 값은 null이다. root의 $schema/description/title은 값 없이 존재/타입만 기록한다. beta는 공개 문서의 고정 기능 이름 8개에 대한 boolean과 나머지 개수만 출력한다. 목록 밖 문자열·메시지 본문·설명·metadata 값·헤더 원문은 출력하지 않는다.

## 현재 — Claude 요청 관찰용 사용자 실행 파일 준비

분석 후 사용자의 자율 진행 지시에 따라 **먼저 실제 요청을 관찰하고, 그 결과로 live 호환 계약을 정하는 순서**를 선택했다. 이 단계에서는 새 로컬 세션 비밀도 Codex OAuth도 전달하지 않는다. `ANTHROPIC_AUTH_TOKEN`에 들어가는 것은 기존 검사기의 공개 상수 `clauduct-public-local-inspection`뿐이다. 이전 env 예외 제안은 이 관찰 단계에 필요하지 않으며 적용하지 않았다.

사용자 별도 PowerShell 터미널에서 한 번 실행한다. 위치 이동이나 환경변수 직접 입력은 필요 없다.

```powershell
node D:\AIDEV\Clauduct\poc\claude-inspection.mjs --inspect
```

[claude-inspection.mjs](./claude-inspection.mjs)는 검사기를 임시 loopback 포트에 열고 고정 경로의 Claude Code를 자식 프로세스로 한 번 실행한다. 작업 디렉터리는 D:\AIDEV\Clauduct다. `-p --model clauduct-poc --tools Read --disallowedTools mcp__* --max-turns 1 --no-session-persistence`와 공개 연결 설정을 전달한다. shell 문자열을 조립하지 않는다. 사용자 인증 파일을 읽는 로더와 Codex 전송 모듈은 이 실행 파일에 없다.

### 실행·출력 계약

1. 부모 환경에서는 명시한 Windows 기본 경로/runtime 변수만 읽어 자식에게 전달한다. 기존 OAuth·API key·임의 환경변수의 값을 복사하지 않는다. 부모 환경과 파일 설정은 수정하지 않는다.
2. 자식 환경과 일회성 `--settings`에 loopback URL·공개 Bearer marker를 넣는다. 자식의 기존 OAuth/API-key/custom-header 변수는 빈 값으로 지정한다. 이는 계정 토큰을 읽거나 지우는 작업이 아니다. 일반 사용자/프로젝트 설정보다 CLI 설정이 우선하지만 관리형 정책을 우회하지 않는다.
3. HTTP/HTTPS proxy를 같은 검사기로 지정하고 127.0.0.1만 예외로 둔다. 검사기는 proxy·CONNECT 요청을 거부하고 외부로 중계하지 않는다. 비필수 통신 억제도 이 자식에만 설정한다. 이는 OS 방화벽이나 모든 hooks의 네트워크 격리가 아니며, 실제 CLI에서의 적용은 사용자 관찰 대상이다.
4. 검사기는 메시지를 정제한 뒤 의도적으로 400을 반환한다. 모델 응답이나 tool_use를 만들지 않아 **이 검사 경로는 Read를 실행하지 않는다**. count_tokens는 404이고 자동 재요청은 기존 8요청·16연결·2capture 상한 안에서만 관찰한다.
5. Claude stdout/stderr 원문은 출력·파일 저장하지 않고 바이트 수만 센다. 합계 256 KiB 초과, 취소, 검사기 종료 시 자신이 시작한 Claude 프로세스를 종료한다. 검사기 최대 60초 + 자식 정리 최대 2초이며 재실행·fallback 없음. hooks가 별도로 만든 자손 프로세스의 전체 종료는 보증하지 않는다.

마지막 **정제 JSON 한 개만 공유**한다. 기대값은 `category=REQUEST_SHAPE_CAPTURED`, `requestCaptured=true`, `resourcesClosed=true`다. `clientExitCode`가 0이 아니어도 검사기의 의도적인 400 응답 때문일 수 있다. 이것은 요청 형태의 관찰 성공이며 실제 도구 왕복 성공이 아니다. `actualReadVerified`는 항상 false다. 공개 marker의 요청이므로 로컬 타 프로세스가 보낸 요청과의 암호학적 구분도 제공하지 않는다.

`NO_MESSAGE_CAPTURED`·시작 실패·취소·출력 상한·정리 실패는 성공으로 바꾸지 않는다. 실패하면 같은 명령을 자동 반복하지 않고 category/clientStarted/clientClosed/clientExitCode 및 observation의 정제 counters/records로 다음 원인을 판단한다. 원문 로그·토큰·설정 파일을 제출하지 않는다.

`acceptedConnections`는 Node의 connection 이벤트 수다. SYN 전체를 측정한 숫자가 아니다. 정상 합성 단일 요청 사례에서는 클라이언트 요청 1회에 실제 HTTP 수신 1회·서버 연결 1회가 관찰됐다. malformedHttp는 정상 HTTP 요청 카운터와 따로 기록한다. 기록 배열은 최대 8개다.

`upstreamRequests=0`, `toolExecutions=0`, `persistedBodies=0`은 해당 동작의 코드가 없는 검사 경로를 설명한다. 외부 패킷 캡처·OS 감사의 측정값으로 표현하지 않는다. Node permission 실행은 파일 읽기/쓰기·프로세스 권한을 제한하지만 Node 24의 네트워크 방화벽이라고 설명하지 않는다.

Expect/100-continue, CONNECT, WebSocket upgrade, HTTP pipelining은 지원하지 않는다. 실제 클라이언트의 자동 재요청 횟수는 아직 측정하지 않았다. 5초 동안 재요청을 못 봤다는 사실만으로 재시도가 없다고 보증할 수 없다.

`betaQuery`는 URL query를 해석해 `beta=true`가 정확히 1개일 때만 true다. 다른 매개변수 뒤의 beta와 percent encoding을 처리하고, `trueevil` 같은 유사 값·다른 값 안의 문자열·중복 beta는 false다. query 원문을 출력하지 않는다. 이 boolean은 진단이며 실제 beta 기능 지원을 뜻하지 않는다.

## 5. 실제 Claude 실행을 열기 위한 조건

설치 경로 `C:\Users\JS\.local\bin\claude.exe`의 FileVersion/ProductVersion은 **2.1.263.0**이었다. 파일 메타데이터를 읽은 증거이며 CLI를 실행한 버전 출력은 아니다. 이전 2.1.261의 결과로 현재 요청 shape를 확정하지 않는다.

1. **인증방식·저장 위치 확인 완료 — 사용자 보고:** Claude Code는 환경변수 `CLAUDE_CODE_OAUTH_TOKEN`으로 MAX 20 PLAN을 사용하고 Codex는 로그인 OAuth를 사용한다. 토큰·계정 상태·플랜 유효성을 에이전트가 검사한 것은 아니다. 관리형 설정은 조사하지 않았으며 추가 질문이나 조사를 현재 게이트웨이 구현의 조건으로 두지 않는다.
2. **실효 목적지 확인:** 단일 사용자 프로세스가 정확한 loopback URL과 공개 fixture marker를 사용하는지 확인할 방법이 필요하다. 저장된 env 설정은 shell env보다 우선할 수 있다. 파일/전역 설정을 바꾸거나 관리형 설정을 우회하지 않는다. [Gateway 연결 문서](https://code.claude.com/docs/en/llm-gateway-connect)
3. **부가 실행·통신 경계 확인:** 기존 hooks/plugins/MCP가 시작 시 수행하는 효과, credential helper와 gateway 밖 요청을 분리해야 한다. 이를 생략하는 `--bare`/`--safe-mode`/설정 출처 제외를 사용해 기존 지침·보안 경계를 없애지 않는다. 현재 문서의 `--tools Read`도 MCP 도구 전체와 EndConversation을 자동 제거하지 않는다. [CLI reference](https://code.claude.com/docs/en/cli-reference)
4. **사용자 실행 1회와 정제 결과:** 위 조건이 닫힌 뒤 사용자 터미널에서 검사한다. 에이전트는 실제 인증을 읽거나 Claude를 대신 시작하지 않는다. 결과는 REQUEST_SHAPE_CAPTURED와 정제 counters/shape만 받는다. NO_MESSAGE_CAPTURED이면 수신 성공으로 가정하지 않는다.

인증방식과 환경변수 저장 위치를 다시 묻지 않는다. 조건 2–3은 실제 Claude 프로세스를 실행할 때의 경계다. Claude 실행 wrapper나 연결 설정을 활성화하지 않았으며 독립적인 게이트웨이 구현·합성 HTTP 검증은 완료했다. 검사기의 사후 거부만으로 전송 전 비노출을 보장할 수 없다.

### 5.1 사용자 보고로 확정한 인증 분리

| 경로 | 사용할 자료 / 결정 |
|---|---|
| 기존 Claude MAX 사용 | 현재 `CLAUDE_CODE_OAUTH_TOKEN`과 기존 로그인 상태를 유지. 이번 작업에서 읽기·변경·로그아웃하지 않음 |
| Claude → 로컬 요청 검사기 | 별도 사용자 실행의 공개 Bearer marker만 사용할 후보 경로. 실제 Claude OAuth와 Codex OAuth를 검사기로 보내지 않음. 아직 실제 Claude에 설정하지 않음 |
| Clauduct → Codex | 기존 사용자 실행 검사와 같은 메모리 전용 OAuth 사용 계약을 우선 설계. 에이전트의 인증 접근과 별개이며 guard는 유지. 만료/401 중단, refresh·저장·계정 변경 없음 |
| 새 PKCE/device 로그인 | 첫 PoC의 필수 선행 조건에서 제외. 기존 OAuth의 적합성 문제가 실제로 확인될 때 별도 검토. 새 client 신원·callback 구현을 지금 추가하지 않음 |

현재 [Claude 인증 문서](https://code.claude.com/docs/en/authentication#authentication-precedence)는 `ANTHROPIC_AUTH_TOKEN`을 Bearer로 보내며 `CLAUDE_CODE_OAUTH_TOKEN`보다 우선한다고 설명한다. API key에는 대화형 승인 상태가 개입한다. 따라서 검사기의 공개 marker를 Bearer로 전달하는 경로를 우선 후보로 선택했다. 이 문서상의 우선순위는 설치된 Claude에서 관찰한 실제 요청 증거가 아니다.

향후 사용자 실행을 구성할 때는 자식 프로세스에 실제 OAuth 변수가 전달·재주입되지 않는 전달 계약이 필요하다. 전역 변수를 삭제하거나 토큰을 읽어 저장했다가 복원하지 않는다. 실제 비밀을 인수·env·로그·임시 파일로 새로 옮기지 않는다. 설정 우선순위는 실제 연결 시 검토할 사항이며 현재 게이트웨이 코드의 착수 조건에서 제외한다. [설정 우선순위](https://code.claude.com/docs/en/settings#settings-precedence)

## 6. 새 PKCE가 필요해질 경우의 설계 — 첫 PoC 필수 조건에서 제외

아래는 새 로그인이 필요하다고 결정한 경우에만 적용한다. 기존 Codex OAuth 사용자 운영 경로를 검토하는 단계의 차단 조건으로 client 등록·callback 구현을 요구하지 않는다. 기존 guard를 우회하는 대안은 아니다.

| 항목 | 확정 요구사항 | 착수 전 남은 조건 |
|---|---|---|
| 인증 소유 | 사용자가 브라우저에서 승인하고 Clauduct의 사용자 프로세스가 해당 세션의 Codex OAuth를 소유 | OAuth client 신원·redirect URI·provider 사용 조건 확인 |
| callback 검증 | 고정 loopback 목적지, 요청별 PKCE verifier/challenge·state, 정확한 callback path, 유효시간·일회 처리, 계정 결합 | 구체적인 포트/URI 계약과 정상·오류·재사용·취소 테스트 fixture |
| 토큰 수명 | 메모리 사용, 최초 범위에서 refresh/저장/계정 변경 없음. 만료·401이면 중단 | provider의 만료·계정 필드와 사용자 운영 인증 범위 |
| Claude→Clauduct 인증 | Codex OAuth와 분리한 로컬 세션 인증. 공개 fixture marker를 제품에 재사용하지 않음 | 실제 비밀을 인수/env/로그/임시 파일로 옮기지 않는 전달 방법과 session 종료 거부 검증 |
| 비노출 | token/header/error 원문은 외부 출력에 포함하지 않음 | 로그인 전체 경로의 성공·실패·취소 검토. 같은 refresh 자료의 중복 소유 금지 |
| 과거 거부 경계 | 기존 인증 파일 접근 거부를 새 shell/OAuth/app-server 경로로 우회하지 않음 | 새 설계는 거부된 자격증명 재사용 효과와 독립적이어야 함 |

지금 확정할 수 있는 것은 이 책임·검증 계약이다. 실제 OAuth endpoint 호출, 코드 교환, callback 서버의 활성화, 자격증명 전달은 이번 구현에 포함되지 않는다. 구체적 미해결 조건 없이 자동으로 인증 구현·라이브 실행에 진입하지 않는다.

| 실제 Read 왕복·권한/hooks | 위 제품 경로와 사용자 실행 필요 | 작업 루트의 합성 파일만 Claude Read 1회, upstream 2회, call_id와 marker 일치. 권한 거부는 실패 데이터로 보존. Clauduct 직접 도구 실행 0 |
| 로컬 제품 인증 | 난수 세션 인증 구현·검증 완료 | 메모리 API, Host/Origin·세션 격리·종료 후 거부 확인. 공개 marker는 거부. 실제 CLI로의 비밀 전달은 미통합 |
| 새 PKCE | 첫 PoC에서 제외, 필요시 조건부 | 새 로그인 필요성이 확인된 경우에만 client/redirect/provider 조건과 state/일회성/만료/계정 결합 검토. 기존 로그인 사용 가능성을 확인하기 전에 새 로그인 구현을 필수로 요구하지 않음 |

| OmniRoute 인증 분석의 잔여 | 정적 분석의 한계 유지 | 활성 계정 설정·import 저장·refresh 동시성·web-cookie 전체 감사는 실시하지 않음. 제외한 다중 계정/영구 저장/cookie 기능의 추가 구현·감사를 Clauduct 최소 PoC의 선행 작업으로 확대하지 않음 |
| 헤더 누락 원인·공식 지원 | 원인 미확정, 조사 종료 | 기존 사용자 3회 증거와 strict FAIL 유지. 인증 대안이 헤더 문제를 고친다고 가정하지 않음. 공식 지원은 로컬 검사로 획득할 수 있는 완료 조건이 아님 |

이전 TTY 종료 검사를 게이트웨이 구현의 선행 조건으로 요구하지 않는다. 사용자 운영 인증 연결부는 구현했으며 다음 수용 작업은 사용자가 실행한 새 게이트웨이 도구 프로토콜 JSON의 분석이다. 실제 Claude 요청 계약의 지원 확장·CLI 비밀 전달은 남아 있다. 기존 guard와 실제 실행의 비노출 경계는 유지한다. 전체 제품의 완료 조건과 현재 증거는 [전체 명세](../verification/최소-어댑터-PoC-명세.md)에 유지한다.
