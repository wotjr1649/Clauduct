# 버전 드리프트 내성

## 관측

2026-09-11 조사에서 이 게이트웨이가 상류 버전 변화에 노출된 축이 셋임을 확인했다.

| 축 | 조사 결과 |
|---|---|
| Codex clientVersion | `poc/user-session.mjs`가 시작 시 `codex --version`으로 동적 취득한다. 기준값과 다르면 비차단 stderr 경고만 낸다. 자동 추종하므로 조치 불요 |
| Claude 모델 이름 | 별칭 4개와 `claude-{haiku,sonnet,opus,fable}-*` 접두사만 매핑한다. 새 계열은 매핑되지 않는다 |
| Claude Code beta 헤더 | `NATIVE_BETAS` 14개만 허용했다. 알 수 없는 beta 하나면 **모든 요청이 400**이 되어 세션을 쓸 수 없었다 |

설치된 codex의 standalone 패키지는 `0.154.0`이며 Clauduct가 전송하는 clientVersion과 같다. 즉 첫 번째 축은 기준 클라이언트를 그대로 따라간다.

사용자가 최신 모델·최신 버전만 사용한다고 확정했으므로 두 번째와 세 번째 축은 반드시 움직인다. 이것이 미지의 이벤트 재발보다 발생 가능성이 높은 다음 고장 지점이다.

## 변경

beta 정책만 바꿨다. 모델 이름 정책은 [별도 감사](audit-2026-09-11-unmapped-agent-model.md)에 있다.

- 이 프로젝트가 비호환으로 판정한 29개 beta는 계속 거부한다. 형식이 잘못된 헤더도 계속 `INVALID_BETA_HEADER`다.
- 한 번도 본 적 없는 beta는 통과시킨다. beta 헤더는 upstream으로 전달되지 않으며, 요청 필드·도구·응답 이벤트는 각각 독립적으로 엄격 검증된다. 따라서 그 beta가 실제로 계약을 바꾸면 통과가 아니라 더 구체적인 라벨의 거부로 이어진다.
- 통과한 이름은 종료 JSON의 `unknownBetaNames`에 최대 8개까지 중복 없이 기록한다. 소문자로 시작하는 `[a-z][a-z0-9-]{0,63}` 형태만 기록하며, 세션 내 상태 API에서는 제거한다. beta 값은 upstream이 아니라 로컬 Claude 바이너리가 생성한 문자열이라 이벤트 이름과 신뢰 경계가 다르지만, 상한과 형태 검사는 동일하게 적용한다.

## 남은 위험

알 수 없는 beta가 켜졌다고 가정하는 클라이언트 동작(새 요청 필드, 새 응답 기대)은 보장하지 않는다. 그런 경우 기존 검증이 거부하므로 조용한 오작동이 아니라 진단 가능한 실패가 된다. `unknownBetaNames`를 보고 allowlist를 보완하는 것은 여전히 사람의 판단이다.

## 검증

`Invoke-ClauductNodeTests`(60초 제한, Node.js v24.19.0). `test-native.mjs` 45개 검사에서 전체 allowlist 통과, 비호환 판정 beta의 400 거부와 `known=FILES_API unknown=1` 메시지, 처음 보는 beta의 200 통과와 이름 기록, 대문자 등 형태 미달 값의 미기록, 도구 변경 beta가 알 수 없는 beta와 함께 와도 기능이 유지되는지를 확인한다. 기준 11개 파일과 선택·완료 표면 4개가 모두 통과했다. 외부 추론 요청·실제 인증 조회·실제 Claude 실행은 0이다.
