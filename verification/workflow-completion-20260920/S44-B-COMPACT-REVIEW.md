재시작 재개 근거를 확보했다. 아래는 그 실증 전의 판단과 compact 원인 분석을 보존한 기록이다.

2026-09-20. 사용자 후속 설명을 반영한 판정이다. Esc는 두 시도에서 문제가 없다고 판단해

사용자가 수용한 native 표시·외부 환경 한계를 새로운 차단 조건으로 추가하지 않는다.

이번에는 제품/native 바이너리 변경이나 새로운 inference를 실행하지 않았다. S44 및
같은 제품의 이전 S49 B 자식 기록, 설치된 native 2.1.278의 코드, 공식 문서를 읽었다.

## B의 실제 실행 조건

다음 상태는 서로 다르다.

| 경계 | 뜻 | S44 근거 |
|---|---|---|
| Workflow B child started | B 모델 작업이 시작됨 | journal의 B started, child ID·선택·backend 완료 있음 |
| Bash tool_use 출력 | 모델이 Bash 실행을 요청함 | 13:13:58.729Z, `call_zMgZ4fDmYRNaaWeEmkj2RC5G` |
| native 권한 검토 | 그 명령을 실행해도 되는지 결정 | permissionRequests 1; 결정의 전체 이력은 보존되지 않음 |
| OS 프로세스 시작 | PowerShell이 실제 실행되어 PID/시작 시각을 가짐 | 독립 근거 없음 |
| TaskStop | 부모가 실행 중인 Workflow 중단 요청 | 13:14:17.361Z 호출, 13:14:17.385Z 성공 |
| OS 프로세스 종료·회수 | 해당 PID와 소유 후손이 실제 사라짐 | B의 PID 자체가 미확보여서 대조 불가 |

B의 `S44_B_STARTED`는 명령 문자열 안에 있을 뿐 stdout 또는 실행 중 생성한 파일로
확인되지 않았다. Bash 결과는 `User rejected tool use`, native `toolDenialKind:user-rejected`다.
이 자료는 **B의 OS 명령이 실행됐다는 증거가 아니다**.

반대로 이 문구만으로 사용자가 승인 버튼을 거부했다거나 명령이 절대로 시작되지 않았다고
단정할 수도 없다. 설치된 native의 `createSyntheticErrorMessage`는 일부 `user_interrupted`
abort 경로에도 `user-rejected`를 붙인다. `Rjt`의 중단 분류와 합쳐 볼 때 취소 시 만들어지는
합성 오류가 가능하다. `permissionRequests:1` 또한 요청 누계이지 현재 승인 대기의 증거가 아니다.
앞 보고서의 “승인 대기 중 중단된 흐름과 일치”는 가능한 해석이며 확정 원인으로 격상하지 않는다.

native 도구 실행 경계는 권한 검사 후 `markToolCallStarted`/`tool_dispatch_start`를 거쳐
실제 `e.call`에 도달한다. 이 dispatch 자체도 Bash 안의 OS 프로세스 생성보다 앞이다.
따라서 가장 직접적인 근거는 **실행된 명령 자체가 남긴 고유 시작 표시와 PID**다.

정확한 보충 시험의 합격 조건은 다음과 같다.

1. 새 독립 시험 B의 정확한 공개 명령을 native 권한 화면에서 승인한다. 기존 거부된 B를
   몰래 재실행하거나 전역 allow 규칙/권한 모드를 변경하지 않는다.
2. B 명령이 실행 후 `STARTED`, 테스트 고유 ID, PID, 프로세스 시작 시각을 남긴 것을 확인한다.
   모델이 쓴 설명, 도구 입력 문자열, elapsed time만으로 대체하지 않는다.
3. 그 PID가 살아 있고 대기 명령이 아직 완료되지 않은 시점에 TaskStop을 한 번 호출한다.
4. TaskStop 뒤 해당 PID 및 소유 후손의 종료를 유한 시간 안에 확인한다. PID 재사용을
   피하도록 시작 시각도 대조하며, `FINISHED`가 없다는 것만으로 종료를 증명하지 않는다.
5. 재개에서는 A 기존 결과 재사용, 이미 시작한 B 재실행 0, 미시작 C만 한 번 실행을 확인한다.

native 화면이 foreground Bash 출력을 늦게 보여줄 수 있으므로 시작 표시를 공개 테스트
폴더의 고유 marker 파일에 쓰는 방식이 더 명확하다. 단일 로컬 관측기로 그 파일과 PID를
확인하면 모델에게 주기적으로 확인시키거나 추론 토큰을 소비할 필요가 없다.
이는 필요한 검증 설계이며 이번에 실행했다고 주장하지 않는다.

## compact에서 실제로 늘어난 것은 무엇인가

Claude Code의 `/compact`는 대화를 요약해 공간을 확보하는 기능이다. 압축 파일처럼 매번
원본보다 짧아지는 형식을 강제하는 기능과 동일하지 않다.
[공식 명령 설명](https://code.claude.com/docs/en/commands),
[공식 컨텍스트 관리 설명](https://code.claude.com/docs/en/how-claude-code-works#when-context-fills-up).

S44에서 확인한 값:

| 측정 대상 | 첫 compact | 두 번째 compact |
|---|---:|---:|
| native preTokens | 29,933 | 1,392 |
| native postTokens | 2,516 | 2,603 |
| 보존된 요약 문자열 길이, JS length | 5,596 | 5,848 |
| 요약 UTF-8 바이트 | 7,345 | 7,809 |
| native 소요 시간 | 59.365초 | 45.287초 |

**두 번째 요약 자체가 252자, 약 4.5% 길어진 것은 사실이다.** native 압축 후 추정값끼리도
2,516 → 2,603으로 87토큰 늘었다. 이미 압축된 내용을 새 일반 대화 없이 다시 요약하면서
문장·서식이 다시 생성된 사례다. 수동 compact가 매번 더 짧아진다는 보장은 없으며,
이번에는 두 번째 compact에 추가 공간 절약 효과가 없었다.

다만 **1,392 → 2,603을 전체 실제 backend 입력이 1,211토큰 증가한 것으로 해석하면 안 된다.**
설치된 native 코드에서 서로 다른 계산 경로를 확인했다.

- `PYn`: pre 값은 `Lg(messages)`를 사용한다.
- `Lg`: 마지막 assistant usage를 기준으로 그 뒤 메시지의 추정량을 더한다. usage 기준점이
  없으면 메시지 추정량을 사용한다.
- `Rie`: 압축 뒤 보존하는 assistant의 이전 input/output/cache usage를 0으로 초기화한다.
- `mI`: 요약 뒤에 보존 메시지·복원 attachment를 배치한다.
- `Ign`: post 값은 그 새 묶음 전체에 `ig(mI(result))` 추정을 적용한다.

첫 pre 값 29,933은 직전 실제 input 29,921 + output 12와 일치한다. 첫 compact 뒤에는
보존 assistant의 usage가 초기화되고, 두 번째 compact 전 일반 생성도 없다. 이때 pre의
usage 기준점 뒤 추정과 post의 전체 새 묶음 추정은 비교 범위가 달라질 수 있다. 특히 요약이
보존 assistant 앞에 배치된 구조에서는 pre 기준점 이전 요약이 같은 방식으로 합산되지 않는다.
이 차이는 native 계산 경로의 한계이며 Clauduct가 실제 backend 입력을 1,392라고 측정한 것이 아니다.
원래 전체 token window가 확대된 것도 아니다.

실제 일반 응답에 기록된 backend input은 다음과 같다.

| 시점 | 모델 | 실제 input_tokens |
|---|---|---:|
| 첫 compact 직전 `S44_BEFORE_COMPACT=17` | Sol | 29,921 |
| 두 compact 후 `S44_AFTER_COMPACT=29` | Terra | 12,833 |

두 관측 사이 실제 입력은 17,088토큰 적다. 전체 대화가 계속 증가했다는 결과는 아니다.
단, 모델·요청·부가 내용이 달라진 두 관측이므로 이를 동일 조건의 순수 압축률이나
두 번째 compact 단독의 backend 절감률로 발표하지 않는다. 첫 compact 직후 같은 모델의
일반 응답은 없어서 두 번째 compact만의 정확한 backend 전후 차이는 이 기록으로 확정 불가다.

## 정책·출시 판정

첫 요약은 기존 이력을 줄였고, 두 번째 반복 요약은 소폭 길어졌다. 두 수동 압축 뒤 대화는
정상 이어졌고 API 실패/반복 자동 압축/이전 이력 전부 재주입의 근거는 없다. 필요한 내용을
보존하는 대신 반복 요약이 약간 길어질 수 있는 성질로 분류한다. 사용량이 충분히 낮고 새
대화가 없다면 연속 수동 compact를 할 실익은 없다. 일반 사용에서는 현재 예방 압축 정책을
유지하며 수치를 낮추기 위해 원문을 자르거나 native 표시를 덮어쓰지 않는다.

Esc에 관한 사용자 설명은 실사용상 문제없음으로 수용하되 미실행한 37 회복을 검증 완료로
작성하지 않는다. 이 설명 이후 집중해서 보충할 항목은 **B의 실제 OS 실행 중 취소·회수 한 범위**다.
현재 자료로 그 범위를 사후 복원할 수 없으므로 새 실패가 없다는 이유로 전체 합격으로 바꾸지 않는다.
S44 관측 기능은 합격, 전체 엄격 수용은 미완료, v0.3.0 최종 출시 승인은 보류한다.

이번 검수의 변경은 보고서·관측 스크립트·판정 JSON뿐이다. 제품 수정/재빌드/추가 구독 요청은 없다.
설치 native 코드의 SHA256·검사한 함수 위치는 판정 JSON에 남겼으며 추출 코드는 실행하지 않았다.
