## Verdict: CLOSED — for the no-pending TUI notification

I reviewed only the excerpts; I ran no tests.

**The chain is now closed at index 0.** In `prepareParentWait`, `workflowLaunch` is gated on `step.Index > 0`, so for a root task-notification turn (`id == ""`, `step.Index == 0`) with `len(readiness.Pending) == 0`, both disjuncts of `step.waiting` are false. `writeParentDecision` then publishes `Wait: hold && step.waiting` = `false`. Native reads `held = decision.wait` = `false`, takes `p.phase='progress_unconfirmed'` with `notification_consumed`, and the `finally` (guarded by `!held`) fires `request_returned`; `turn.complete` then sets `turn_ended` because `p.phase!=='awaiting_children'`. The hold still happens (the empty reply is still swallowed, `answer:''`, `stopReason:null`) — only the lifecycle phase is decoupled from it, which is exactly the conflation F1 named.

Worth noting for robustness: the escape from `awaiting_children` on this path is done by the `finally`, not by `turn.complete`. So even a turn that never completes cleanly ends in `progress_unconfirmed`/`tool_pending`, never `awaiting_children`.

**Pending-child TUI behavior preserved.** `len(readiness.Pending) > 0` ⇒ `waiting=true` ⇒ `wait:true` ⇒ `held=true`, `children_wait`, `finally` skipped, and `turn.complete` retains `awaiting_children` only for `reason==='answer'`. Unchanged.

**SDK preserved.** The SDK branch returns before `held` is ever assigned, so `held` stays false and the `finally` always ends progress, while the attributed status text and `end_turn` still go out. SDK parents therefore never sit in `awaiting_children`, consistent with "native owns the next notification."

**Validation is strictly stronger, not weaker.** `decision.hold && (!eligible || typeof decision.wait!=='boolean')` now rejects a held control that omits or mistypes `wait`; a held control still must be an empty terminal reply (`CONTROL_INVALID` otherwise); turn/index mismatch still degrades to `{hold:false}`. `wait` is not forgeable from native: `parentStep.waiting` is unexported and absent from the `readNativeJSON` allowed-key list (`session, agent, turn, index, eligible, mode`), so it can only come from the gateway snapshot. The `hold && step.waiting` form also guarantees the pre-write (`hold=false`) always publishes `wait:false`, so no stale `wait:true` survives for the same turn/index.

The test is a real regression check, not a tautology: `waiting=true` only reaches the assertion through the `native_tui` branch (the SDK branch would yield `turn_ended`), and running `false` after `true` proves the new-turn `p` reset actually drains a leftover `awaiting_children`.

## One residual introduced by this correction (not the notification path)

`workflowLaunch` is the only way `waiting` becomes true with zero pending children, and its only liveness condition is `!origin.rejected` — it never checks that the correlated workflow still has unfinished children, and the entry stays in `workflowCalls`/`workflows`. A root continuation at `index>0` whose trailing tool boundary is a Workflow launch that spawns nothing, or whose children all finish before that continuation is admitted, gets `wait:true` with no notifier left to start the next turn and reset `p`. That is a launch/tool-result turn rather than a notification, so it does not reopen F1 as scoped, but it is a new non-self-healing case that the pending-child path does not have (there, every pending child eventually notifies). If you want it bounded, the cheap fix is to require the correlated run to have no delivered terminal state before counting it as a wait.
