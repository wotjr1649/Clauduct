# 세션 33 — 출하 기준 재정리

## 목표

2026-09-14 사용자 범위 변경의 **필수성 판단은 이미 내려져 있다**(`docs/release-priority-assessment-2026-09-14.md:7-13`). 그런데 그 판단이 나머지 현행 문서로 **전파되지 않았다.** 세 자리가 여전히 "F12·F14·F22 세 사유로 전체 HOLD"로 읽힌다.

이 세션은 두 가지를 한다.

1. 판단을 나머지 문서로 전파한다.
2. 그 범위 변경과 **아직 대조된 적 없는** `docs/remaining-verification.md` 3장의 5개 행을 판정한다.

**판정 권한의 경계**: "무엇이 왜 남았는가"는 이 세션이 확정해 문서에 남긴다. **"HOLD 해제"나 "출하 PASS" 표기는 하지 않는다** — 근거를 모아 제시하고 선언은 사용자가 한다. 저장소가 반복해 경고하는 "완료를 위장해 도구 상태를 바꾸지 않는다"와 같은 선이다.

대화형이다. 막히면 묻는다.

## 지금 참인 것

- main `2a54511`. 로컬·원격 동기화, 열린 PR 없음, CI 초록.
- 워크플로는 `push: branches: [main]` + `pull_request:`다. **커밋당 CI 런이 1개**이며 PR이 열리지 않은 브랜치는 빌드되지 않는다.
- 마지막 전수 통과(세션 32, 로컬): `verification/test-*.mjs`와 `poc/test-*.mjs` 11개 파일 전부 초록, `GATE_STATUS=0`. 머지 후 main CI도 통과했다.
- `verification/test-dotnet-http-transport.mjs`는 정상 통과에도 **49초**가 걸린다. `deadline-45s`가 의도적으로 45초를 쓰기 때문이며 지연이 아니다.
- **실호출 예산 잔여 0**이다(최종 요청 cap 327). 추가 실호출은 예약돼 있지 않다.
- untracked 33개, worktree 6개. 전부 보존 대상이다.

## 작업 1 — 전파

권위 있는 출처는 `docs/release-priority-assessment-2026-09-14.md:7-13`의 판단표다. 대상 5개에 대해 "일반 개발에 필수인가"와 "현재 목표에 대한 결정"이 적혀 있다. **이 판단은 사용자 지시로 내려졌다. 새 증거 없이 다시 열지 않는다.**

전파되지 않은 자리:

| 자리 | 현재 읽히는 내용 |
|---|---|
| `docs/release-completion-2026-09-14.md:45` | F12·F14·F22 세 건이 "원문에서도 미완료/차단 보존을 요구한다" |
| `docs/unattended-release-progress.md:11` | "F12 부모 직접 알림, F14 Workflow 재개, F22 동적 링크 정책 차단 때문에 **전체 HOLD**다" |
| `docs/remaining-verification.md:56` 이하 3장 | 현행 기준인데 범위 변경이 반영돼 있지 않다 |

`docs/release-completion-2026-09-14.md`는 `:11`에 F22 제외를 적어놓고 `:45`에 옛 문장을 남겨 **한 문서 안에서 모순된다.**

새 문서를 만들지 않는다. 기준이 또 하나의 문서로 쪼개지는 것이 지금 고치려는 문제 자체다. **결과 위치는 제안이며** 더 나은 자리가 보이면 바꾸되 이유를 적는다.

F 번호의 정의는 `docs/research-2026-09-12-unattended-release-gates.md:163`(F12)과 `:165`(F14)다. 요약이 아니라 이 정의를 기준으로 판정한다.

## 먼저 읽을 것 — 이 작업을 통째로 틀리게 만들 수 있는 것

`docs/unattended-release-progress.md`는 **최신 문단이 위에 쌓이고 "이력"·"과거"를 인라인으로 표시하는 구조**다. 시간 순서가 파일 순서가 아니다.

- `:7` 후속 사용자 변경 — F22 제외, F12·F14 완화
- `:11` 2026-09-14 최신 마감 — **여기가** "F12·F14·F22로 전체 HOLD"를 말한다
- `:13` 상태 — "출하 HOLD(미완료)"
- `:17` 출하 기준 변경 — 2026-09-14 사용자 직접 지시

`:11`의 HOLD 문장이 그것을 수정하는 문단들 **사이에** 있다. 문단 하나만 읽고 결론을 내면 틀린다. **각 문단의 날짜와 "이력"·"과거" 표기를 먼저 확인해 시간 순서를 세운 뒤에 판정한다.**

## 제약

- **실호출 0.** 재정리가 실호출을 요구하는 결론에 이르면 쓰지 말고 블로커로 보고한다. 예산은 사용자가 준다.
- 검증 어서션을 약화시켜 통과시키지 않는다. 가드와 검증 대상을 먼저 구분한다.
- `git add -A`나 `git add -- docs`를 쓰지 않는다. 변경한 파일을 하나씩 이름으로 stage한다.
- **사용자의 기존 untracked 파일은 임의 삭제·stage·덮어쓰지 않는다**(`HANDOFF.md:141`). untracked 33개, worktree 6개 전부 유지 대상이다.
- 권한 계층이 거부하는 것: `git push origin --delete`, `git reset --hard`, `git push --force-with-lease`. **다른 도구로 우회하지 않는다.** 원격 정리는 사용자에게 명령을 제시한다.
- AdGuard가 켜져 있으면 loopback HTTP test 5건이 실패한다. 제품 결함이 아니다. 판별법은 `docs/native-startup-diagnostics-2026-09-14.md`.
- 문서를 쓰면 `verification/test-doc-citations.mjs`의 검사 두 가지를 통과해야 한다.
  - `파일:줄` 인용 — 파일 존재·범위·빈 줄을 본다. **줄이 옮겨갔는지 직접 확인한다.** 검사기는 "존재하는 다른 코드"를 가리키는 인용을 구분하지 못한다.
  - 마크다운 링크 — 저장소 내부 상대 경로는 **git이 추적하는 경로**여야 한다. `.tmp/` 링크는 실패한다(세션 32가 그래서 14건을 고쳤다).

## 배경 사실 — 작업 항목이 아니다

세션 32가 남긴 두 가지다. 재개 조건이 문서에 적혀 있으니 **재발할 때 집어든다.**

1. `verification/DotnetHttpProbe.cs:211`의 `normal` 예산 120000이 충분하다는 증명은 없다. 이전 관측 31486ms는 30000 예산에서 끊긴 **검열된** 값이라 실제 지연을 모른다. 같은 지점이 120000에서 또 걸리면 값을 올리지 말고 케이스마다 node 파서를 띄우는 구조를 본다. 전말은 `docs/audit-2026-09-15-ci-spawn-latency.md`의 5-1.
2. `파일:줄` 인용은 코드가 움직일 때마다 드리프트한다. 세션 32에서만 2회 발생했고 검사기는 못 잡는다. 고칠 방향은 줄 번호 대신 내용 일부를 함께 검사하는 것이다. 지금은 열려 있지 않다.

## 세션 32가 한 일 (배경)

인계받은 3건을 닫았다. `deadline-45s` 상한은 CI 실측 5건(45002~45017ms)과 "이 경로에 spawn이 없다"는 코드 근거로 **변경 없이** 닫았다. `read_extra_normal`은 진단을 먼저 넣자 `open: sockets`라고 스스로 말했고, `poc/gateway.mjs`의 소켓 스냅샷이 원인이었다 — 종료 순서는 건드리지 않았다. 링크 검사를 추가했다. 계획에 없던 것으로, main이 빨간 상태(`sse-fixed` 재발, 31486ms)라 감사 5-1 절차대로 기록·분류·수정했다. PR #15·#16·#17·#18.

## 완료 기준

- 세 자리의 낡은 HOLD 서술이 현행 판단과 일치한다.
- 3장의 5행 각각에 제외·이관·유지 중 하나가 **근거와 함께** 적혔다.
- **남은 필수가 무엇이고 왜 남았는지가 한 자리에서 읽힌다.**
- 측정 없이 추정한 항목은 **추정으로 표시**한다.
- HOLD 해제·출하 PASS 표기는 하지 않는다. 근거를 제시하고 사용자 판단을 받는다.
- 변경한 문서가 `node verification/test-doc-citations.mjs`를 통과한다.
