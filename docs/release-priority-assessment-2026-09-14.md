# 부모 알림과 Workflow 재개의 필수성 판단

2026-09-14 사용자 요청에 따라 동적 symlink/junction 실행 검사를 출하 기준에서 제외한다. F22 전체의 신원·경로·기록 재사용 검증을 없애는 뜻은 아니다. 실제 검사 차단 이력은 그대로 보존하며 PASS로 바꾸지 않는다. **이 문서는 Session-29 착수 시점의 처방전이다 — 현행 잔여 목록이 아니다.** 아래 판단표는 무엇이 필수인가를 정하고, 아래 두 절은 그때 해야 할 일을 적는다. `:36`의 소스 서술은 `1c3e569` 이전 상태다. 그 처방은 Session-29가 수행했고 현행 잔여는 [현행 검증표](remaining-verification.md)의 3.2절에서 읽는다.

## 판단

| 대상 | 일반 개발에 필수인가 | 현재 목표에 대한 결정 |
|---|---|---|
| 자식 결과·실패를 올바른 작업에 연결 | 필수 | 결과 회수·실패 보존·중복 처리 방지는 유지 |
| native가 중간 부모에게 직접 보내는 비동기 알림 | 전달 방식 자체는 필수 아님 | 동일한 결과를 제공하는 명시적 수집/메인 중계를 해결책으로 삼는다. 직접 알림의 실패 이력은 유지하고 기존 중계 성공을 전체 실패·취소 경로의 성공으로 확대하지 않는다 |
| 저장 기록이 남은 Workflow 정상 재개 | 일반 편집·Agent 사용에는 필수 아님 | 기존 Workflow 지원과 장애 후 개발 지속이라는 약속을 유지하려면 해결할 항목으로 남긴다 |
| Workflow 기록 전체 소실 뒤 자동 복원 | 필수 아님 | native도 자동으로 다시 시작하지 않는다. 명시적인 재개 불가와 효과 확인이 정상 결과이며, 기록 없이 성공을 복원하도록 만들지 않는다 |
| 동적 링크 실행 검사 | 기본 기능의 필수 구현은 아님 | 사용자 지시로 출하 판정 제외. 관련 제품의 경로 보호 코드는 유지 |

부모 직접 알림과 Workflow 재개를 모두 일반 코드 편집의 필수 기능이라고 설명했던 것은 지나치게 넓었다. 현재 main→Agent→main 왕복과 신규 Workflow는 실제로 통과했다. 문제인 부모 알림은 main→부모 agent→자식 agent로 중첩하고, 중간 부모의 턴이 끝난 비동기 경로다.

현재 source의 역할도 구분해야 한다. Clauduct는 모델 요청을 변환하고 검증한다. native 내부 스케줄러가 생성하지 않은 알림을 gateway 수정만으로 원래와 동일하게 발화시킨다고 약속할 수는 없다. [공식 subagent 문서](https://code.claude.com/docs/en/sub-agents#resume-subagents)의 재개 후 중간 부모 보고 설명도 interactive 세션에 한정되어 있다. 이 설명을 `-p`의 보장으로 확대하지 않는다.

## 부모 알림의 최소 해결 방향

권장안은 기존 결과 수집과 `SendMessage` 중계를 재사용하는 것이다. 부모가 실행 중이면 반환된 task ID의 `TaskOutput`으로 결과를 수집한다. 부모의 턴이 이미 끝났으면 메인에서 검증한 자식 결과와 부모 관계를 확인해 기존 부모를 재개한다. 자식 작업을 새로 생성해 결과를 다시 얻는 방식은 사용하지 않는다.

기존 실제 증거를 다시 읽었다. luna/max15요청·sol/low14요청의 `CompletionMode=relay` 실행은 각각 부모1/직접 자식2, SendMessage1회, verified-resume1회, 부모 완료와 cleanup이 PASS였고 직접 notification 수는0이었다. 이는 중계 경로가 가능한 근거다. 다만 `verification/completion-relay-target.mjs`는 고정 공개 성공 문구와 자식2개를 검증하는 시험용 코드다. 현재 일반 제품에 모든 실패·취소 중계가 완성됐다는 뜻은 아니다.

후속 구현·검증은 성공/실패/취소를 구분하고, session·parent·child·현재 요청을 연결하며, 한 결과를 한 번만 처리하는 데 한정한다. 사용자 취소는 자동 재개하지 않는다. 실패를 성공 결과로 전달하지 않고, 부모 관계를 확인할 수 없으면 명시적으로 보존·중단한다. 검증할 최소 사례는 정상 성공, 자식 실패, 중복 알림, 오래된 요청 알림, 형제 혼입, 사용자 취소다. 고정 공개 응답과 실제 native로 먼저 검사하고, 관련 동작 변경을 확인한 뒤 필요한 실제 두 조합만 시험한다. 같은 직접 알림 실패를 반복하거나 대기 시간을 늘리는 방향은 권장하지 않는다.

## Workflow 재개의 최소 해결 방향

[공식 Workflow 재개 문서](https://code.claude.com/docs/en/workflows#resume-after-a-pause)에 따르면 저장된 결과를 재사용하는 정상 재개와 재실행 대상이 존재한다. 반면 저장 결과가 전혀 없으면 `nothing to resume`로 끝난다. 따라서 “cache miss”를 모든 기록 소실과 같은 뜻으로 사용하면 출하 기준을 잘못 잡게 된다. 또한 재개가 이전에 완료된 모든 agent의 재실행0을 보장하는 기능은 아니므로, 효과를 쓰는 단계는 별도의 대조가 필요하다.

기존 공개 probe의 원자료에서 첫 sum5 완료와 script 편집 뒤 두 번째 Workflow가 실패한 사실을 확인했다. native2.1.269 오류는 scriptPath가 도구가 반환한 script 경로 또는 이미 읽을 수 있는 경로여야 한다는 검사였다. 이 사례는 `nothing to resume`나 파일 없음 오류가 아니었다. 관리자 권한 부족·Windows 결함·기록 소실로 단정하지 않는다. 당시 전달한 경로와 native 등록값의 정확한 일치는 아직 확인하지 못했다. 거부된 읽기를 다른 표기·경로·권한으로 재현하지 않았다.

작업은 두 층으로 나눈다.

1. native가 반환한 구조화된 run/task/script 필드를 근거로 경로 신원을 확인한다. 설명문 속 사용 예제를 권한 근거로 삼지 않는다. 기존 읽기 검사 조건을 유지한 상태에서 정상 접근 조건을 확정해야 한다. 재개 시 run ID·task ID·journal이 실제로 어떤 형태로 바뀌는지 관측하기 전에는 같은 ID 또는 append 형식을 가정해 구현하지 않는다.
2. Clauduct의 재개 신원 연결을 구현한다. `src/agent-route.mjs`와 `src/agent-selection.mjs`는 현재 신규 inline script만 근거로 사용하고, `src/workflow-selection.mjs`는 이미 연결한 run ID를 다시 받지 않는다. 경로 허용 문제만 없어져도 이 공백은 남는다. 검증된 이전 실행, 재개 호출, 새 실행 세대와 자식을 연결하고 이전 자식 기록으로 새 요청을 승인하지 않도록 해야 한다.

최소 수용 사례는 저장 결과만 재사용하는 재개, 일부 agent가 다시 필요한 재개, 같은 세션을 새 프로세스에서 이어가는 경로, 이전 worker 생존 시 중복 실행 거부, 다른 세션·변조·오래된 기록 거부, 전체 기록 소실 시 안전한 재개 불가다. 실제 파일/도구 효과가 있었다면 해당 효과를 확인한 후에만 재실행한다. 임의 Bash/MCP에 보편적인 exactly-once를 주장하지 않는다.

## 우선순위와 현재 수행

판정 우선순위는 동적 링크 제외 반영 → 부모 직접 전달과 필수 결과 처리의 구분 → Workflow의 정상 재개 계약 확정이다. 구현에서는 이미 검증된 부모 중계를 출발점으로 재사용하고, 더 큰 제품 공백인 Workflow 재개 신원 연결에 우선순위를 둔다. 기록 전체 소실의 자동 복원이나 native 직접 알림 강제 구현을 새 목표로 확장하지 않는다.

이번 작업은 계약·현재 source·기존 공개 실행 증거·공식 문서의 분석과 출하 기준 기록 변경이다. 제품 동작, 권한, 기존 시험 결과와 ZIP은 변경하지 않았다. 실제 backend 추가 요청0·인증 읽기0이며 기존 누적 요청327/상한327을 유지한다. 부모/Workflow 개선의 구현 완료나 전체 출하 PASS를 선언한 것은 아니다.
