## 후속 모델 정책 변경: sol/xhigh 및 명시 선택 경로 분석

사용자가 sol 기본 effort를 xhigh로 변경했다. src/models.mjs의 단일 기본값을 갱신해 메인 기본 선택, 요청 모델 기본값, Plan 역할 배정에 적용했다. Haiku/Sonnet→luna, Opus→sol 별칭은 유지한다. 메인의 명시적 --effort high는 계속 존중하며 compact 전용 medium 정책도 유지한다. README와 native.md의 현재 기본값만 갱신하고 과거 sol/high 실제 결과는 보존했다.

Verified: launcher-native에서 sol 기본 xhigh, native 실행 인수, 세 별칭, subagent의 sol 기본값과 Plan 경로를 검사했다. 명시 high 보존 검사도 통과했다. compact-policy 통과, native 42/42 통과. 실제 Claude 실행·인증 읽기·외부 요청은 없으며 sol/xhigh 실제 계정 수락은 미검증이다.

명시 모델 우선 처리는 아직 미구현이다. 설치 native의 SubagentStart 구성에는 agent_id/agent_type이 있지만 명시 모델 여부나 부모 Agent tool_use_id가 없다. PreToolUse에는 tool_input/tool_use_id가 존재하나 이를 자식 agent_id와 확실히 연결하는 경로를 아직 입증하지 못했다. 현재 gateway는 등록 역할 route를 요청 doc.model보다 우선한다. 따라서 도착 순서나 부모 모델과의 단순 비교로 명시 여부를 추정하면 병렬 요청 또는 같은 모델 명시 선택에서 잘못 배정할 수 있다. 모델 우선순위 한 줄을 바꾸는 수정은 하지 않았다. 다음 구현에는 Agent 호출과 자식 요청을 모호성 없이 연결하거나 native 모델 선택 단계에서 기본값을 적용할 수 있는 경로 검증이 필요하다.

추가 정적 근거: 설치 native의 rx 모델 선택 경로는 호출 override를 agent 정의보다 먼저 처리한다. ADn은 CLAUDE_CODE_SUBAGENT_MODEL_FORCE가 켜졌을 때 override를 제거하고, Agent 입력 schema도 model 필드를 생략한다. 현재 점검한 프로세스 환경 및 사용자 settings.env에는 이 강제 옵션과 coordinator 강제 상속 옵션이 없었다. 프로젝트 .claude 설정 파일도 해당 경로에 없었다. 실제 별도 터미널 환경이나 관리형 설정 전체까지 검사한 것은 아니다. modelOverrides는 모델 ID→provider ID 치환 기능으로 역할별 미지정 기본값 문제를 해결하는 옵션이 아니다. 따라서 해당 옵션을 새로 적용하거나 native 강제 정책을 해제하지 않았다. 보완 지점은 native가 이미 보존하는 모델 선택을 gateway가 다시 덮어쓰지 않게 하되, 미지정 역할 기본값을 잃지 않는 공통 경로다. Agent 직접 호출 외에 fork Skill과 workflow 생성도 별도로 고려해야 한다.

공식 문서 https://code.claude.com/docs/en/sub-agents 도 대조했다. --agents는 prompt와 agent 정의 필드를 받는 세션 전용 custom agent 정의이며 native 정의에 model만 병합하는 기능이라는 근거는 확인되지 않았다. CLAUDE_CODE_SUBAGENT_MODEL은 공통 기본값으로 명시 모델보다 후순위지만 역할마다 다른 기본값을 표현하지 못한다. FORCE를 켜면 명시 선택까지 제거하므로 승인된 설계와 충돌한다. fork 및 model:inherit인 fork skill은 별도 상속 경로이므로 Agent 도구 인수만 수정해 전체 경로 해결을 주장할 수 없다. 전역 설정이나 built-in agent prompt를 대체하는 변경은 하지 않았다.

현재 판정: 핵심 Read 왕복·수동/검증 창 자동 compact·역할별 모델 배정과 hook 환경 상속은 실제 증거를 확보했다. 제품 전체 검증 완료는 아니다. 아래 기록은 시간순이며 과거의 미검증 표기는 후속 실제 증거로 보완될 수 있다. 현재 검증 범위는 native.md의 '검증 범위와 남은 공백'을 함께 확인한다.

## 잔여 목표와 시간 진단

이전 구현 목표 complete는 전체 실제 운용 검증 완료를 뜻하지 않는다. 사용자 지적에 따라 compact 지연 계측 및 실제 자동 압축/서브에이전트 검증을 남은 활성 목표로 등록했다. 실제 인증 갱신과 수시간 장기 실행은 이번 단계에서 제외했다.

gateway는 최근 모델 요청 16개의 숫자·고정 model/effort·역할 구분·시각만 메모리에 보관한다. 시작부터 입장 대기, 본문 준비, transport 진입, 첫 upstream event/text delta, 첫 downstream write, transport 반환, 종료 시점과 최대 5개 retry 예약 시각을 제공한다. 본문·인증·헤더·reasoning을 저장하지 않는다. transport 진입은 실제 소켓 전송 시작이 아니며 인증 조회와 재시도 대기를 포함할 수 있다. retryScheduledMs는 예약 시각이며 실제 재전송 횟수와 동일하다고 해석하지 않는다. downstream write는 화면 렌더링 완료 시각이 아니다.

업데이트된 Clauduct 자식에서 `node D:/AIDEV/Clauduct/src/request-status.mjs`를 실행하면 인증 값은 출력하지 않고 고정 loopback의 시간 진단만 읽는다. 종료·재시작하면 기록은 사라지므로 검증 요청 직후 수집한다. 기존 실행 중 gateway에는 소급 적용되지 않는다. 새 수집 명령은 합성 gateway로 검사했으며 실제 native 자식 환경에서 실행한 것은 아니다.

추가로 `attempts`에 실제 HTTP 시도별 최대 6개 기록을 제공한다. 각 시도의 startedMs/requestFlushedMs/headersMs/firstBodyMs/endedMs는 해당 transport.send 내부 시작부터의 상대 밀리초다. status는 HTTP 코드이며 completed는 transport 응답 정상 종료 여부다. requestFlushedMs는 Node의 요청 쓰기 완료 이벤트로 서버 수신 완료를 뜻하지 않는다. gateway 필드들은 gateway 처리 시작 기준이므로 원점을 혼동하지 않는다. 이 기록으로 첫 시도 이전 처리, 시도 사이 지연, 응답 헤더 전 대기, 본문 수신 구간을 나눌 수 있으나 원격 서버 내부 queue/prefill/reasoning 시간은 분해할 수 없다.

다음 실제 검증은 업데이트된 실행기로 기존 세션을 resume해 `/compact`를 수행한 직후 진단을 수집하는 것이다. 자동 압축 실제 발동과 서브에이전트 상속은 별도 수용 조건이며 수동 compact 성공으로 대체하지 않는다.

## compact effort 최적화와 잔여 검증 준비

사용자의 후속 개선/목표 재개 요청으로 작업을 재개했다. 목표 API는 기존 목표를 blocked로 반환하며 active 전환 기능이 제공되지 않는다. 새 목표 생성도 미완료 목표가 있다는 이유로 거부됐다. 이를 우회하려고 기존 목표를 complete로 변경하지 않았으며 목표의 미완료 범위를 유지한다.

공식 문서 조사와 설치 native 정적 코드에서 compact 전용 model/effort 설정은 확인되지 않았다. 설치 코드의 x-cc-compaction-request 헤더는 first-party 목적지에만 붙으므로 loopback에서 사용할 수 없다. 숨은 first-party 위장 옵션은 사용하지 않는다.

`compact-policy.mjs`에서 설치 2.1.263의 _0e/yPn compact wrapper 시작·끝 텍스트가 최종 user 메시지에 정확히 일치하는 경우만 compact-template로 분류한다. 기존 모델은 유지하고 일반 라우팅 이후 effort가 high/xhigh/max이면 medium으로 낮추며 low/medium은 유지한다. 이는 공식 origin 판별이 아닌 버전 의존 템플릿 호환 경로다. 과거 이력/assistant/tool_result는 분류하지 않으며 템플릿 변경 시 기존 effort를 유지한다. 동일 템플릿 직접 입력도 분류될 수 있으므로 인증·권한 판단에는 사용하지 않는다. 요약 프롬프트나 도구 권한은 변경하지 않는다.

진단에 purpose, requestedEffort(일반 라우팅 후 compact 조정 전 값), 실제 effort, role/roleRegistered를 추가했다. request-status의 clientContextPolicy는 알려진 세 환경 숫자만 출력하며 환경 상속 증거라고 명시한다. 이를 실제 backend context capacity 증거로 확대하지 않는다.

`--verify-auto-compact`는 자식 실행에만 AUTO_COMPACT_WINDOW=100000을 적용한다. 모델 창 500000 및 기본 percentage는 유지하며 출력 예약량 20000 조건에서 약 66666에 발동하는 계산이다. 일반 실행은 원래 정책으로 돌아가고 부모/전역 설정은 그대로다. dry-run에서 실제 Claude나 인증을 열지 않고 검증 창 설정을 확인했다.

Verified: 새 compact-policy 검사에서 네 모델·세 역할의 compact 조정과 일반 기본값 보존, low 유지, 과거/인용/변형 템플릿 배제, 실제 loopback gateway에서 compact medium 다음 일반 max 복원과 진단 출력을 확인했다. launcher-native, native-protocol, gateway 15/15, native 41/41, chat 26/26도 통과했다. 실제 compact 성능 개선·요약 품질·새 템플릿의 live 일치와 자동 발동/서브에이전트 상속은 아직 미검증이다. 후속 순서는 remaining-verification.md에 정리했다.
