# Session-13: 3회 연속 로컬 개발·검증 시험

## 목표와 작업 경계

Node.js 표준 라이브러리만 사용하는 로컬 작업 관리 CLI를 개발한다. 아래 3개 플랜을 같은 세션에서 순서대로 구현·검증·로컬 커밋하고 종료한다. 회차 사이에 사용자에게 continue나 승인을 요구하지 않는다. 이것은 Clauduct를 이용한 실제 개발 시험이며 Clauduct 자체를 수정하는 작업이 아니다.

유일한 쓰기 대상은 D:/AIDEV/Clauduct/verification/dev-sandbox/run-02이다. 이 문서는 읽기 전용 입력이다. run-01, Clauduct 소스·문서·부모 저장소의 Git 상태, 전역 설정은 변경하지 않는다. 실행 권한은 현재 사용자 요청과 호스트 정책을 따른다. 이 문서는 권한을 확대하지 않는다.

사용자는 장기개발을 일반적인 개발 플랜과 검증을 최소 3회 연속 수행하는 것으로 정의했다. 비용은 미정이다. Pro plan에서 이번 작업을 끝낼 수 있는지는 미검증이며 사용량 제한을 우회하거나 유료 계정·API로 전환하지 않는다. 시간 채우기, 인위적 대기, 추가 회차, 자동 반복 시험은 하지 않는다.

## 최초 확인: 짧게 한 번

1. 현재 디렉터리와 적용되는 지침을 확인한다. 작업 루트가 없으면 위 정확한 경로에 생성한다. 루트가 비어 있지 않으면 기존 작업을 읽기 전용으로 확인하고 충돌 가능성을 보고한 뒤 중단한다. 임의로 삭제하거나 다른 run으로 바꾸지 않는다.
2. Node.js와 Git 사용 가능 여부를 확인한다. node:test를 사용할 수 없으면 설치하지 않고 중단한다. 루트가 빈 디렉터리이고 그 안에 .git이 없으면 이 루트에만 git init을 수행한다. git rev-parse --show-toplevel의 정규화된 경로가 run-02와 일치하는지 확인하기 전에는 stage/commit하지 않는다. 부모 저장소에서 git 명령을 실행하지 않는다. Git identity가 없으면 설정을 변경하지 말고 중단한다.
3. 현재 모델·effort는 변경하지 않는다. 프로세스 기본값이나 astra/max를 가정하지 않는다. 호스트가 제공하는 값은 출처를 붙이고, 실제 실행 경로를 확인할 수 없으면 Not verified로 적는다. 세션 ID/sessionRef는 확인 가능한 경우만 기록한다. 인증·원본 세션·전체 환경을 탐색하지 않는다.

위 확인 후 바로 개발을 시작한다. 무관한 문서 탐색, 외부 검색, 설치, 제품 전체 사전 검증을 하지 않는다.

## 개발 계약

ES modules, node:test, node:assert 및 Node.js 표준 라이브러리를 사용한다. 의존성 설치·서버·네트워크 기능은 필요 없다. package.json의 test는 node --test로 실행 가능하게 한다. CLI 진입점은 cli.mjs, 사용법은 README.md에 둔다. 필요한 내부 파일 구조는 최소한으로 정한다.

CLI 예시는 node cli.mjs add "첫 작업"이다. 저장 경로는 작업 루트 안의 data/tasks.json을 기본으로 하며, 테스트는 루트 안에서 자신이 생성한 별도 임시 디렉터리를 사용한다. 테스트용 저장 경로를 선택하는 방법은 제공하되 루트 밖에는 쓰지 않는다. symlink/junction 생성 시험은 하지 않는다. 단일 프로세스·직렬 쓰기만 지원하며 동시 writer 지원을 주장하지 않는다.

작업에는 양의 정수 ID, 제목, 상태(todo/done), 태그 배열이 있다. ID는 삭제되지 않은 데이터에서 충돌하지 않게 증가한다. 빈 제목·잘못된 인수·없는 ID는 명확한 오류와 0이 아닌 종료 코드로 처리한다. 사용자 문자열을 shell 명령으로 실행하지 않는다. 저장 파일이 없으면 초기 상태로 시작하지만 잘못된 JSON이나 데이터 형식은 오류로 처리하고 원본을 덮어쓰지 않는다. 쓰기 실패 시 기존 정상 데이터를 보존하는 최소한의 저장 방식을 사용한다.

## 플랜 1 — 기본 작업 관리

add <title>, list, show <id>를 구현한다. 새 작업 상태는 todo이고 태그는 빈 배열이다. list는 ID 오름차순이다. 별도 CLI 프로세스로 다시 실행해도 저장된 작업이 조회되어야 한다.

검증: 빈 목록, 작업 2개 생성과 고유 ID, 조회, 재실행 후 영속성, 빈 제목, 없는 ID, 알 수 없는 명령, 손상된 저장 파일의 오류 및 원본 바이트 보존. 라이브러리 테스트 외에 실제 CLI 프로세스를 호출하여 stdout/stderr/exit code와 저장 결과를 확인하는 테스트를 포함한다.

통과하면 관련 파일만 로컬 커밋하고 플랜 2로 진행한다.

## 플랜 2 — 상태 변경과 검색

done <id>, reopen <id>, rename <id> <title>, tag <id> <tag>를 추가한다. 동일 상태 재지정과 동일 태그 재등록은 중복 데이터를 만들지 않는다. list에 --status todo|done, --tag <tag>, --query <text>를 추가하고 함께 사용하면 AND 조건으로 적용한다. 검색은 제목의 대소문자 구분 없는 부분 일치이며, 태그는 정확히 일치한다. 태그는 비어 있지 않은 문자열로 제한한다.

검증: 상태 왕복 변경, 같은 작업 반복의 멱등성, 이름 변경, 중복 태그, 개별·조합 필터, 잘못된 상태·빈 태그·없는 ID. 플랜 1 전체 테스트도 다시 실행한다. 기존 저장 데이터는 유지되어야 한다.

통과하면 관련 파일만 로컬 커밋하고 플랜 3으로 진행한다.

## 플랜 3 — 집계와 데이터 내보내기

summary는 전체·todo·done 개수와 태그별 작업 수를 JSON으로 stdout에 출력한다. export는 전체 작업을 ID 오름차순의 JSON 배열로 stdout에 출력한다. 두 명령은 저장 파일을 수정하지 않는다. README에 설치 불필요 실행법, 모든 명령, 오류 동작, 단일 writer 제한을 정리한다.

검증: 빈 데이터 집계, 혼합 상태·태그 집계, 한글·따옴표·개행을 포함한 제목의 JSON 왕복, export 정렬, 읽기 명령 전후 저장 파일 바이트 동일성, 모든 이전 회차 테스트. 별도 시험 데이터로 add → tag → done → 필터 조회 → summary → export의 실제 CLI 시나리오도 실행한다.

통과하면 관련 파일만 로컬 커밋하고 최종 보고 후 종료한다. 네 번째 플랜은 만들지 않는다.

## 진행·중단 규칙

각 회차에서 짧은 계획 → 구현 → 테스트 → 필요한 수정 → 누적 회귀 검증 → diff 확인 → 로컬 커밋을 수행한다. 테스트는 실행당 60초 이하의 timeout을 적용한다. 최초 검증 이후 회차당 수정·재검증은 최대 3회이며, 새 근거 없이 같은 목표가 3회 연속 실패하면 그 전에 중단한다. 통과한 테스트를 실패 숨기기 위해 삭제·완화하거나 가짜 결과로 대체하지 않는다.

서브에이전트·Workflow는 필수가 아니다. 호스트 지침상 허용되고 독립적인 읽기 전용 검토에 실익이 있을 때만 사용한다. 같은 파일의 동시 쓰기를 만들지 않는다. 사용할 경우 등록된 정의의 모델·effort 계약을 유지하며, inherit는 자식 생성 시점의 직접 부모 모델·effort를 따른다. 이름이나 요청값만으로 실제 라우팅 성공을 주장하지 않는다. 사용하지 않은 경로는 미검증으로 기록한다.

사용자 개입, 사용량 제한, 해소되지 않는 인증 오류, 권한/guard 거부, 루트 이탈 필요, 기존 변경 충돌, 완료 여부가 불명확한 중복 실행 위험이 생기면 해당 실행을 중단하고 상태를 보고한다. 거부된 효과를 다른 도구로 재현하지 않는다. 인증 갱신·모델 변경·자동 재시작·무한 polling을 하지 않는다. 사용자 중단 후에는 추가 도구를 호출하지 않는다. push/PR/배포, 전역 설정·hook·권한 변경은 하지 않는다.

정상적인 context compaction이 발생하면 저장된 코드·검증 기록과 Git 상태를 확인해 남은 회차만 이어간다. 강제로 compact하거나 프로세스를 죽이는 시험은 이번 정상 완주 시험에 섞지 않는다. 사용자가 재개를 지시한 실행은 연속 무인 완주와 구분한다.

## 증거와 최종 판정

루트의 VERIFICATION.md에 회차마다 요구사항, 실제 실행 명령, exit code, 테스트 통과/실패/skip 수, 수정한 실패와 남은 위험을 기록하고 해당 회차 커밋에 포함한다. 전체 출력이나 비밀을 복사하지 않는다. 시간은 관측 가능한 시작·종료 시각만 기록하고 비용·토큰을 확인할 수 없으면 unknown으로 쓴다. 검증 기록을 먼저 저장한 뒤 커밋하며 커밋 hash는 최종 답변에서 git log로 확인한다.

최종 답변은 회차별 실제 결과와 커밋 hash, 전체 테스트 결과, 작업 루트와 git status, 실제 세션 식별자(확인 가능한 경우), 사용자 개입 유무, 사용한 Agent/Workflow 및 모델 경로의 확인 수준을 보고한다. Verified / Not verified / Blocked by를 구분한다.

3개 플랜이 실제 테스트·로컬 커밋까지 완료되고 최초 지시 이후 사용자 도움 없이 이어졌을 때만 THREE-CYCLE-PASS라고 적는다. 안전 정지는 SAFE-STOP, 검증 실패는 FAILED로 적으며 완료한 회차와 남은 회차를 명시한다. 안전 정지와 개발 성공을 혼동하지 않는다.

이번 통과는 3회 연속 개발 능력의 증거다. 별도 중단·복구, 장시간 자원 누적, 모든 모델·Workflow, 보안 격리 전체 또는 제품 전체 완료를 입증하지 않는다. 시험 결과는 후속 조사자가 실제 세션 기록과 대조한다.
