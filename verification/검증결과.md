## 현재 — DUPLICATE_UPSTREAM_HEADER

native transport가 모든 raw 응답 헤더 이름의 유일성을 요구하던 결함을 확인했다. 이전 PoC는 Content-Type 중복만 검사한다. 부가 헤더는 소비·저장·전달하지 않으므로 반복을 허용하고 payload 해석에 관여하는 Content-Type/Content-Encoding/Content-Length/Transfer-Encoding 중복은 계속 거부한다. Node 기본 HTTP 파서의 잘못된 framing 거부도 유지한다.

**Verified:** loopback HTTP에서 Set-Cookie/Cache-Control/Vary 반복 응답이 수정 전 실패(native 38 통과/1 실패), 수정 후 성공(native 39/39)했다. 혼합 대소문자 중복, Content-Type/인코딩 충돌, 길이/전송 형식 중복 거부와 자원 정리를 검사했다. 응답 본문에 합성 cookie 값이 포함되지 않는 것도 확인했다. **Not verified:** 사용자의 실제 중복 헤더 이름 및 실제 Claude/Codex 응답 완료. 실제 Claude/인증 읽기/외부 요청은 0회다.

## 현재 — clauduct 대화형 실행기 구현·로컬 검증 완료

## 이전 단계 — 사용자 PROTOCOL_REJECTED 보고 분석, 진단 결함 수정·로컬 검증 완료

**사용자 실행 증거:** 사용자가 node-https-gateway / upstreamMode=live의 정제 JSON을 제공했다. passed=false, category=PROTOCOL_REJECTED, gpt-6-astra/xhigh, clientVersion=0.153.4, requestAttempts=1, connectionAttempts=1, compatibilityApplied=0, resourcesClosed=true, callIdMatches=false, exactMarker=false, toolResultMode=synthetic, toolExecutions=0, credentialWrites=0, retries=0이다. 이 보고에는 HTTP 상태·헤더 상태·세부 파서 오류가 없었다. 이전 OK 비교의 HTTP 200을 이 실행의 상태로 옮겨 적지 않는다.

**확인한 진단 결함:** PROTOCOL_REJECTED는 서버가 보낸 문구가 아니라 gateway의 고정 대체 오류명이다. gateway와 사용자 진입점의 허용 목록에서 여러 실제 파서 오류가 빠져 구체 원인이 사라졌다. 합성 HTTP 200 응답에 sequence_number=7을 넣은 검사로 수정 전 상세 코드 전달 실패를 재현했다. 공유 오류 목록을 사용한 수정 뒤 같은 검사는 SEQUENCE_MISMATCH를 최종 사용자 JSON까지 전달했다. 이는 진단 결함의 해결이며 사용자 라이브 응답 호환성 해결을 입증하지 않는다.

compatibilityApplied는 본문 전체가 통과한 응답 수이므로 0만으로 헤더 정책이 사용되지 않았다고 판단할 수 없다. callIdMatches/exactMarker=false도 성공 확인을 얻지 못했다는 뜻이며 실제 ID 불일치·잘못된 답변의 증거가 아니다. 사용자 실패의 구체 원인은 여전히 미확정이다. reasoning 항목 등 미지원 구조는 로컬에서 확인한 가능한 실패 경로이지 이번 사용자 응답의 관찰값이 아니다.

### 사용자 실행 결과 — Node https와 fetch 비교

이 절은 이번 이관에서 사용자가 제공한 두 실행의 정제 결과 요약이다. 에이전트가 인증을 읽거나 실제 계정 요청을 실행한 결과가 아니며 응답 원문을 확보한 것도 아니다. 기존 Node 라이브 검사를 다시 요구하지 않는다.

|---|---|---|
| HTTP / 전체 판정 | 200 / `passed=false`, `MISSING_CONTENT_TYPE` | 동일 |

| 본문 진단 | `sseDiagnostics.passed=true`, `SUCCESS` | 동일 |
| 모델 / effort 응답 필드 | `modelMatches=true`, `effortEchoMatches=true` | 동일 |
| 답변 출처 / 정확 일치 | `replySource=stream`, `exactOK=true` | 동일 |
| 완료 output_text / delta / text done | 0 / 1 / 1, 위치별 내용 일치, `reconstructed=true` | 동일 |

모델/effort 필드 일치는 내부 추론 강도의 독립 측정이 아니다. 두 구현은 Node/TLS 기반을 공유하므로 서버와 공통 통신 경로 중 누가 헤더를 생략했는지는 미확정이다. 같은 6,242바이트가 원문 동일성이나 캐시 사용을 입증하지 않는다. U2Bio가 원인이라는 증거도 없다.

사용자가 별도 터미널에서 실행한 `dotnet-httpclient`의 정제 JSON 1건을 제공했다. 아래는 사용자 실행 증거이며 에이전트가 인증에 접근하거나 요청을 대신 실행한 결과가 아니다.

`contentTypePresent=false`는 .NET이 제공한 헤더 컬렉션에서 필드 부재를 보고한 것이다. 단순히 값이 비어 있다는 증거와 구별한다. 완료 메시지가 없어 `replyEmpty=true`, `streamMatchesCompleted=false`인 반면, delta와 text done이 일치해 `exactOK=true`로 복원된 것은 모순이 아니다.
요청·연결 숫자는 검사기의 클라이언트 카운터다. 실제 upstream 서버의 수신 로그나 TCP SYN 전체를 독립 계측한 값으로 표현하지 않는다. 전송 설정 필드 역시 검사기에 지정된 설정이며 실제 통신 경로의 모든 중간 계층을 관찰한 결과가 아니다.

| Node fetch | Headers 컬렉션에서 부재 | SUCCESS / 정확한 OK 복원 | FAIL / MISSING_CONTENT_TYPE |

결론: 구현을 .NET으로 바꾸고 HTTP/1.1·자동 proxy 비사용으로 실행해도 같은 분류가 관찰됐다. 특정 Node HTTP 구현만의 문제라는 설명을 뒷받침하지 않는다. 서버, 공통 네트워크 경로, 로컬 통신 계층 중 어디서 헤더가 생략됐는지는 여전히 미확정이며, .NET 결과만으로 어느 하나를 원인으로 확정하거나 배제하지 않는다. 세 응답의 같은 바이트 수·이벤트 수·usage도 원문 동일성이나 캐시 사용의 증거가 아니다.

**조사 중단 결정:** 동일 목적의 추가 라이브 검사·헤더 원인 조사 확대를 수행하지 않는다. 전체 FAIL과 기존 엄격한 성공 조건을 유지한다. 사용자 결과 반영 시점에는 G1을 닫고 G2를 미해결로 남겼다. 이후 별도 사용자 승인으로 결정한 G2의 제품 opt-in 정책은 상단 후속 구현 절에 기록했다. 원래 비교 결과는 바꾸지 않는다.

직전 사용자 결과 반영 단계에서는 이 문서와 `최소-어댑터-PoC-명세.md`만 갱신했다. 당시 코드·검사·schema는 변경하지 않았고 라이브·회귀 검사를 다시 실행하지 않았다. 제공된 정제 필드와 기록의 일치, Markdown/로컬 링크, 미관련 파일의 해시 보존을 확인했다. 이후 승인받은 오프라인 구현은 상단에 별도로 기록했다.

로컬에서 관찰한 버전은 PowerShell **7.6.5**, .NET **10.0.11** (`System.Net.Http` informational version `10.0.11+e2f47b0110ed922f21a1522da67279133ce28f32`), Node **24.19.0**, Undici **7.29.0**, Codex CLI **0.153.4**다. .NET 진입점은 위 PowerShell/.NET 버전을 고정 확인하며, 라이브 경로는 CLI/Node 버전도 확인한다. 버전 변경 시 자동 업데이트·제한 완화 없이 중단한다.

고정 endpoint/model/effort/prompt와 명시적 비인증 헤더/JSON 본문은 기존 Node 생성 함수의 값과 로컬 서버에서 비교했다. 사용자 라이브에서만 같은 형식의 Authorization·chatgpt-account-id를 사용한다. 이후 사용자 실행으로 HTTP 200과 기대한 모델 응답을 보고받았다. 인증 헤더 원문이나 서버 인증 판단을 에이전트가 독립 확인한 것은 아니다.

.NET 비교 설정은 해당 HttpClient 인스턴스에만 적용한다.

- `RequestVersionExact`의 HTTP/1.1, 새 handler와 연결 1개, `Connection: close`, `ExpectContinue=false`를 사용한다. HTTP/2·3 협상/스트림 재시도를 비교에서 제외한다.
- `ConnectCallback`은 최초 연결만 허용하고 재연결은 소켓을 열기 전에 거부한다. 응답 내용이 URL이나 목적지를 바꾸지 못한다. `requestAttempts`는 SendAsync 호출 수이고 서버 도착 증명은 아니다. `connectionAttempts`는 Socket.ConnectAsync 호출 수이며 DNS 후보별 SYN 횟수가 아니다. 실제 테스트 서버에서는 매 사례 HTTP 수신 1회·TCP 연결 1회를 확인했다.
- `AllowAutoRedirect=false`, `UseProxy=false`, `UseCookies=false`, `Credentials=null`, `DefaultProxyCredentials=null`, `PreAuthenticate=false`, `AutomaticDecompression=None`이다. 자동 proxy 검색/OS 인증/cookie 재사용/압축 해제를 사용하지 않는다. 환경·시스템 proxy 설정 자체는 수정하지 않는다.
- 인증서 검증 callback이나 trust store를 설정하지 않는다. HTTPS의 TLS와 인증서 검증은 HttpClient 기본 동작에 맡긴다. 전역 TLS·proxy·방화벽·보안 프로그램 변경은 없다. Windows/.NET의 TLS 구현과 자동 헤더·연결 특성은 Node와 같다고 가정하지 않는다.
- `ResponseHeadersRead` 이후에도 같은 취소 토큰을 send/body read/로컬 parser에 전달하여 요청 단계 45초를 제한한다. 버전 확인과 사용자 SEND 대기 시간은 요청 제한 밖이다. 로컬 parser 자식 프로세스는 별도로 최대 7초이며 남은 45초 예산도 넘지 못한다.
- 응답 본문은 256 KiB, 초과 확인용 1 byte를 읽으면 실패한다. 응답 헤더는 16 KiB다. 정규화하지 않은 .NET 헤더 컬렉션 `NonValidated`에서 Content-Type 존재와 빈 값을 구별하며 원시 wire 헤더 API인 것처럼 보고하지 않는다.
- `MaxResponseDrainSize=0`, `ResponseDrainTimeout=0`으로 폐기 후 본문 배출 대기를 없앤다. 첫 검사에서 취소 후 소켓이 1초 뒤에도 남아 실패했고, 이 설정 뒤 같은 소켓 종료 검사를 통과했다. 실패 검사나 시간 조건을 완화하지 않았다.

이 방어가 필요한 근거는 .NET 10.0.11의 [연결 재시도 상수](https://github.com/dotnet/runtime/blob/v10.0.11/src/libraries/System.Net.Http/src/System/Net/Http/SocketsHttpHandler/ConnectionPool/HttpConnectionPool.cs)와 [HTTP/1 처리 소스](https://github.com/dotnet/runtime/blob/v10.0.11/src/libraries/System.Net.Http/src/System/Net/Http/SocketsHttpHandler/HttpConnection.cs)에서 확인했다. 연결 제어는 [ConnectCallback](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.socketshttphandler.connectcallback?view=net-10.0), 별도 본문 시간 제한은 [HttpCompletionOption](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpcompletionoption?view=net-10.0), 응답 폐기 시 배출 제한은 [MaxResponseDrainSize](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.socketshttphandler.maxresponsedrainsize?view=net-10.0)를 대조했다. 재시도 루프를 직접 작성하지 않았다는 사실만으로 요청 수를 주장하지 않는다.

인증/응답은 메모리에서만 사용하며 명령 인수·환경 변수·로그·임시 파일에 복사하지 않는다. .NET이 인증을 가진 요청·연결을 폐기한 뒤 응답 status, Content-Type, 제한된 body만 고정 Node 파서의 비공개 stdin에 전달한다. base64는 이 로컬 파이프의 바이트 보존용이며 비밀 제거 수단이 아니다. 실행 파일·인수·경로·제어 흐름은 응답 내용으로 선택하지 않는다. .NET/Node 런타임의 debug·preload·trace/TLS 재정의로 확인 가능한 설정은 값을 출력하거나 해제하지 않고 거부한다. managed 문자열의 즉시 완전 소거까지 보증하지는 않는다.

### Not verified / Blocked by — 현재 남은 경계

**Not verified:** 헤더 누락 원인과 전체 HTTP 호환성 통과, 실제 Ctrl+C, backend 도구 호출, 실제 Claude 왕복. .NET 라이브 응답은 위 사용자 증거로 확인했지만 에이전트가 실제 HTTPS/TLS·인증·SEND 입력을 독립 실행하거나 관찰하지 않았다. 재연결 차단 callback의 두 번째 호출 분기는 통신 사례에서 발생하지 않았고, 비교하지 않은 모든 OS/네트워크 실패까지 실측한 것은 아니다. 기존 Node 전송의 실제 45초 만료를 이번 .NET 시간 검사로 대체하지 않는다.

**Blocked by:** 이전 `credential-path` guard의 에이전트 인증 접근 거부는 계속 미해결이다. 이번에 인증 읽기·라이브·SEND를 재시도하지 않았다. 버전 확인용 중첩 PowerShell 명령 1건은 `ps-nested-shell` guard에 거부되어, guard가 안내한 직접 PowerShell 명령으로 버전만 확인했다. guard·전역 설정을 바꾸지 않았다.

다음 단계의 확정 요구사항과 착수 조건은 [최소 어댑터·PoC 명세](./최소-어댑터-PoC-명세.md)에 있다. .NET 비교 결과는 확정했고, 헤더 정책·제품 인증 경계·Claude 버전/실제 요청·자동 재요청·token count fallback은 여전히 조건부다.

## 직접 HTTP 경로 — 사용자 실행으로 답변 복원 확인, 헤더 누락 원인 미확인

연결 방식 재검토 후 직접 HTTP 중계를 우선 검증하기로 했다. 아래 app-server/hook 결과는 이전 후보의 기록이며 직접 HTTP 검사의 필수 조건이 아니다.

### 상세 진단 — 이전 단계에서 추가

인증 접근·모델 요청·전역 설정 변경 없이 기존 검사기, 오프라인 검사, 이 문서만 수정했다.
`headerDiagnostics`는 Node의 정규화된 Content-Type 값이 비어 있지 않은지와 `rawHeaders`의 이름 위치에 Content-Type이 있는지를 별도로 출력한다. 헤더 값은 출력하지 않으며, 원시 헤더 자료가 없거나 잘못된 형식이면 존재 여부는 `null`이다.
원시 헤더에 없다는 사실도 서버와 중간 계층 중 누가 생략했는지를 특정하지는 않는다.

완료 응답을 읽은 경우 `textDiagnostics`에 다음을 출력한다. Content-Type이 없으면 `sseDiagnostics.textDiagnostics` 아래에 있다.

| 필드 | 의미 |
|---|---|
| `outputTextPartCount` | 완료 응답에서 발견한 output_text 조각 수 |
| `replyEmpty`, `replyChars` | 추출 텍스트의 빈 문자열 여부와 Unicode 코드 포인트 수(화면상 글자 수와 다를 수 있음) |
| `trimmedOK` | JavaScript trim()으로 앞뒤 공백을 제거했을 때 OK인지. 정확 일치 성공 조건을 대체하지 않음 |
| `deltaEventCount`, `deltaShapeValid` | output_text.delta 이벤트 수와 문자열/위치 인덱스 형식 검사 결과 |
| `streamChars` | 유효한 delta를 위치별로 합친 텍스트의 코드 포인트 수. 잘못된 delta가 있으면 null |
| `streamMatchesCompleted` | 출력/내용 인덱스별 delta와 완료 텍스트의 정확 일치 여부. delta가 없거나 형식이 잘못되면 null(비교 불가) |

텍스트·헤더 원문, 임의 키, 인증값, 계정 정보는 진단에 복사하지 않는다. 위 `replyEmpty`/`replyChars`/`trimmedOK`는 계속 완료 이벤트에서 추출한 텍스트의 진단이다. 아래 복원 단계의 `exactOK`/`replySource`와 의미를 구분한다.
완료 응답의 잘못된 항목/내용 구조나 문자열이 아닌 output_text는 문자열 강제 변환·예외 대신 `INVALID_RESPONSE_SHAPE`로 실패 처리하도록 방어 검사를 추가했다.
OpenAI Docs의 [delta/완료 이벤트 예시](https://developers.openai.com/api/reference/typescript/resources/beta/subresources/responses/methods/create)와 Node.js의 [rawHeaders 정의](https://nodejs.org/docs/latest-v24.x/api/http.html#messagerawheaders)를 참고했다. ponytail 기준으로 외부 의존성과 별도 검사 프레임워크 없이 기존 함수와 테스트를 확장했다.

### 이번 변경 — 검증된 스트리밍 답변 복원

`response.completed`가 정확히 한 번 도착하고 status가 completed여야 한다. 완료 메시지가 없는 경우에만, 위치별 delta와 `response.output_text.done`의 위치·텍스트가 모두 정확히 일치하면 복원한다.
기존 완료 메시지가 비어 있거나 다른 답변인 경우 스트림으로 덮어쓰지 않는다. 메시지 구조가 잘못되면 실패한다. 완료 이벤트의 모델과 effort가 각각 요청값과 정확히 일치해야 하며, effort 누락도 이 검사에서는 통과가 아니다(실제 effort 하향을 입증하는 것은 아님).
답변은 output_index/content_index의 숫자 순서로 복원하며, 공백을 제거하지 않은 정확한 OK를 검사한다. reasoning과 텍스트의 같은 위치 점유, delta/done/항목 snapshot의 불일치, 중복 완료, 텍스트 완료 뒤 delta, 전체 완료 뒤 추가 이벤트, 조기 [DONE], 오류·취소·미완료·도구 호출·거부는 실패한다.
이전에 진단만 하던 delta/완료 텍스트 불일치도 이제 성공을 차단한다. 정상이던 최종 텍스트가 있어도 서로 모순되는 스트림은 통과시키지 않는다.

| 결과 필드 | 해석 |
|---|---|
| `replySource=stream` | 완료 메시지 부재를 확인하고 delta+텍스트 완료로 복원한 텍스트를 판정에 사용 |
| `replySource=completed` | 완료 이벤트의 output_text를 판정에 사용 |
| `replySource=none` | 판정에 사용할 텍스트를 확보하지 못함 |
| `exactOK` | 위 선택된 텍스트가 정확히 OK인지 |
| `textDiagnostics.streamExactOK` | delta를 복원한 텍스트가 정확히 OK인지. delta가 없거나 잘못됐으면 null |

헤더가 누락되면 `sseDiagnostics.passed=true`여도 전체는 `passed=false`, `category=MISSING_CONTENT_TYPE`이다. 헤더를 만들거나 검사 조건을 우회하지 않는다.

### 이전 단계 — 사용자 실행용 fetch 비교 구현

## Blocked by — 핵심 기술 검증이 남은 이유

1. 현재 확인한 공식 설정에는 기본 도구 전체를 일괄 제거한다는 계약을 찾지 못했다. 없다고 단정하는 것은 아니다.
2. 실제 로컬 요청을 수신해 보니 `environments: []`에서도 functions.exec 및 collaboration 도구 선언이 남았다. 도구 선언과 실제 실행 허용은 별개이므로 실행이 성공한다고 단정하지 않는다.
3. `dynamicTools` 등록은 클라이언트 도구를 추가하는 인터페이스이지 기본 도구를 대체한다는 보증이 아니다.
4. `read-only`나 모델에게 "다른 도구를 쓰지 말라"는 지시만으로는 단독 실행 주체 조건을 통과시킬 수 없다.

추가 검사에서는 thread/start와 로컬 합성 provider에 대한 turn/start를 호출했다. OpenAI 실제 모델로 보내는 turn은 실행하지 않았다.
기존 지침·보안 hooks·guards를 비활성화하거나 로그인 토큰을 복사해서 이 경계를 우회하지 않았다.
이는 실행 중 거부 오류가 발생했다는 뜻이 아니라, 안전한 추론 검사에 필요한 실행 경계의 증거가 부족하다는 뜻이다.

### 개별 설정 제한의 실측

`--capture-restricted`는 검사 thread에만 shell_tool/unified_exec/multi_agent/view_image/image_generation/browser_use/computer_use/in_app_browser/apps=false와 web_search=disabled를 요청했다.

`--capture-classic`는 추가로 code_mode_host=false를 요청했고 false로 보고됐지만, 여전히 같은 최상위 code-mode/collaboration 선언이 남았다.
설정을 요청한 것과 실효 도구를 구별해야 한다. 이 실험은 로컬 합성 provider에서만 수행했고 전역 설정을 편집하지 않았다.

제한 후 exec의 설명에 남은 중첩 도구 선언은 list_mcp_resource_templates, list_mcp_resources, probe_echo, read_mcp_resource, clock__curr_time, skills__list, skills__read였다.
이는 설명의 선언을 추출한 결과이지 런타임 전체 목록이나 실행 차단의 증명은 아니다.
전체 input에서 exec_command 문자열이 발견된 사실만으로 exec_command가 실제 등록됐다고 주장하지 않는다.

이후 승인된 검사 전용 PreToolUse allowlist 정책의 현재 상태는 문서 상단에 기록했다.
기존 hooks 보존 및 단위 검사는 통과했지만, 신뢰 절차 때문에 Codex 실행 검사는 진행하지 않았다.
